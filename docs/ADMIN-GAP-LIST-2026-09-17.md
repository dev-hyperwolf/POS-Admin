## B. The three named modules, in depth

### Tax
- Vendor: two near-identical Mongoose schemas across repos — `Tax.js` (nested city/county/state/federal, each with its own `status` toggle, `taxRate`, `taxDispalyName`) at `hemp-backend/models/Tax.js` and `stilo-backend/models/Tax.js`; plus a simpler flat `TaxSettings.js` (single `taxRate`, `retailerId`) in both repos. Applied at order time via `admintTaxDataAndCalculateTotals`/`attachTaxDataAndCalculateTotals` (`stilo-backend/controllers/order/order-controllers.js:761-785,3072-3103`), looked up by `storeId` (`stilo-backend/controllers/product/tax-controllers.js:9`) and by `memberType` (`:26`, `getTaxByMemberType`). Cannabis excise vs general sales tax are separate sub-objects, not one blended rate. Admin screens: `hemp-retailer-admin/src/components/settings/TaxManagement/{TaxManagementView,TaxTable,TaxSetting,AddTaxManagement,TaxTableNonCannabis}.jsx` (cannabis vs non-cannabis get separate tables — `TaxTableNonCannabis.jsx` filename is itself the evidence of that split), plus a separate Metrc-specific tax screen `hyperwolf-super-admin/src/layouts/Metrc/taxes.js`.
- Ours: `pos/data.jsx:428-438` — three hardcoded percentages (local 2.22%, excise 15%, sales 6%) applied to every sale regardless of store, category, or member type. No `Tax`/`TaxSettings` table in wm-demo, no `/api/tax*` route (grepped `wmdemo/server.py`'s 149 `/api/` literals, zero tax hits). `taxBreakdown()` is pure math, consumed by `pos/sales-panel.jsx:57,117,122` and `pos/screen-cart.jsx:1365`.
- Gap: real tax needs per-store rate rows and a cannabis/non-cannabis split at minimum; member-type branching is a stretch goal (vendor has it, but INFERRED low usage — not confirmed live in any doc read).
- Smallest build: a `tax_rates` table in wmdemo (store_id, category, rate_type, rate, active) + `/api/tax/rates` CRUD + swap `pos/data.jsx:428`'s constants for a fetched table, same shape as region_menus. Belongs in wmdemo's `catalog.py` neighborhood (store/category config), not a new module.

### Regions
- Vendor: three shapes, not one. `hemp-backend/models/Region.js:1-15` — flat + `kml` string field + `openingHours`/`closingHours` numbers. `hyperdrive-backend/models/Region.js:1-40` — geometric: `latitude`/`longitude`, `companyId` ref, `active`. `distribution-backend/models/Regions.js:1-14` — just a name + `platform` enum (`hyperwolf`/`stilo`) + embedded `subRegions[{subRegionId, driverId}]` array (validation at `:15-27`). Screens: `regions` appears in BOTH `hyperwolf-super-admin/src/layouts/regions` and `hemp-retailer-admin/src/layouts/regions` (super-admin also has `distributionSetting`, `distributor` for the delivery side). No single canonical Region — this matches `census-ours.md`'s broader finding of 120 collection names, 70 duplicated across repos.
- Ours: `wmdemo/catalog.py:97` `regions` table is a driver-assignment lookup (region name -> driver), explicitly the documented "mock seam" (`catalog.py:6`: "regions/zips -> KML zones... would be real"). Routes `/api/region` (`wmdemo/server.py:5009`) and `/api/region-menu` (`:5021`) exist and are live per `census-ours.md` section C (pos app dir is LIVE-leaning). No geometry, no KML, no hours anywhere in wm-demo.
- Gap: no delivery-zone polygon/KML at all on our side — this is the same "region -> KML zones + Airtable" gap `catalog.py:6`'s own comment names as the real dependency, i.e. the vendor code and our own code AGREE this is mocked; it isn't a doc-vs-code contradiction.
- Smallest build: import the vendor's `kml` string field onto our `regions` row and reuse the existing GAS/Airtable KML zone lookup (already live per prior handoff docs — `distribution-engine`/GAS side, not rebuilt) rather than porting `hyperdrive-backend`'s lat/long polygon math. Belongs in `wmdemo/catalog.py` (region data owner already).

### Drawers
- Vendor: **no cash-drawer/register-close model exists anywhere in the 12 hyper-tech repos** — grepped `*drawer*`/`*cashdrop*`/`*float*`/`*shift*`/`*cashclose*` across all repos; every "Drawer" hit is a UI slide-out panel (`CommonDrawer`, `CartDrawer`, `NotificationDrawer`), not a cash drawer. Blaze prints a closing receipt used as the reconciliation anchor (`CASH-DROPPED-COUNTED-VERDICT-2026-08-17.md:82`) but does not appear to do float/drop math itself. The actual prior art is Hyperwolf's own GAS `end-of-shift-portal/RetailFloatPlan.gs` (`RETAIL-FLOAT-D1-FALSE-BLOCK-2026-08-16.md:10`, `RETAIL_FLOAT_ROLL_COMBO_CAP` at `:13`) plus Airtable `CR`/`CRX` tables and a `Float Amount` field (observed values 50/105/200, `RETAIL-FLOAT-D1-FALSE-BLOCK-2026-08-16.md:177`) and `cashDroppedCounted` payload field (`CASH-DROPPED-COUNTED-VERDICT-2026-08-17.md:36`).
- Ours: `pos/drawer.jsx` (182 lines) + `pos/store.jsx:48-56` implement open/close register with counted-vs-expected variance math client-side; `pos/screen-register.jsx` is 2,360 lines and is the sale path. But `_persistSession` (`pos/store.jsx:24`) is `localStorage.setItem` only — no server table, no `/api/register`/`/api/drawer`/`/api/cash*` route in `wmdemo/server.py` (grepped, zero hits among 149 `/api/` literals). A register close today produces no audit row survivable past the browser tab.
- Gap: this is the widest gap of the three named ones because neither hyper-tech NOR Blaze actually owns this logic — it's 100% Hyperwolf-built (GAS), and our own wm-demo demo hasn't absorbed it yet, so there are two divergent implementations (GAS float planner vs pos/drawer.jsx) that don't talk to each other.
- Smallest build: a `register_sessions` table in wm-demo (store_id, opened_by, float, counted, expected, variance, opened_at, closed_at) + `/api/register/open`, `/api/register/close` mirroring `openRegister`/`closeRegister`'s existing shape (`pos/store.jsx:49-56` already computes the right fields — this is a lift-and-persist, not a redesign) — belongs in a new `wmdemo/register.py`, sibling to `inventory_api.py`.
