## 1. What the research changed

1. **The volume premise is wrong by ~60×.** [measured] Didit's Usage page counts are cumulative:
   ID Verification 9,391 lifetime, **154 this month**; Face Match 7,877 / 153; Passive Liveness
   7,798 / 152. The verifications table holds 2.1K sessions, newest 2026-08-04, and the dashboard
   shows 0 in the last 30 days. Current run-rate is ~150 sessions a month, inside Didit's 500 free
   checks. The $2,657.89 is lifetime spend, $2,223.60 of it the white-label fee. Consequence: the
   engine is sized for bursts of tens per hour, not hundreds; the cost case for leaving Didit is
   independence, not the bill.
2. **The live site never sends `vendor_data`, a callback, metadata or `expected_details`.**
   [measured] `hyperwolf-backend/controllers/didit/didit-controllers.js:123-140` posts
   `{ workflow_id }` only. Correlation lives in the site's Mongo (`BlazeUser.diditSessionId`, keyed
   by email). Imported Didit sessions therefore carry no customer key; people are resolved by
   document + name + DOB (`identity_match.py`) and the unresolved count is reported honestly.
3. **There is no webhook receiver on the site today.** [measured] Status is learned by the
   browser polling `GET didit/retrieve/status` every 8 s, which proxies Didit's decision endpoint.
   An approved user who closes the tab is never recorded. Our pipeline makes the signed webhook
   the source of truth and keeps a polling-compatible facade for the site.
4. **"In Review" completes checkout on the site.** [measured] `checkout-container.tsx:731`. This
   is a policy hole, not a nuance; it is escalation §11.2, and the compatibility facade defaults
   to translating `In Review` to "keep waiting" unless the owner rules otherwise.
5. **The site uses a raw iframe to `verify.didit.me`, no SDK.** [measured] `next.config.ts:80`
   CSP `frame-src`. Our hosted capture page must be iframe-embeddable from `www.hyperwolf.com`
   and complete without `postMessage`. Site change = three env vars + one CSP host.
6. **The live workflow id is an env var on the dev team's box** [measured, value unknown]. The
   console's newest sessions are all on "Hemp Verification (no selfie)", so the env var probably
   still points at the sunset hemp workflow. Escalation §11.1: confirm which workflow to mirror.
7. **The estate already has a verification model to reuse, and no image storage at all.**
   [measured] `pos/verification.jsx` (T0/T1/T2 assurance ladder, expiry rules), `identity_match.py`
   (5-tier matcher), `verify_gate.py` (fail-closed transaction gate wired into `engine.py`),
   `bind_gate.py`, `checkin.py`. Only a sha256 of the document number persists; `IdPhotoCapture` is
   a file input producing Blob URLs, not a camera. `DiditProvider` in `verify.py` has zero callers
   and says a `didit` row is "a claim somebody posted".
8. **Didit's console vocabulary is exact and small.** [documented] Ten status literals, V3
   decision arrays keyed by `node_id`, `X-Signature-V2` HMAC over a canonicalised body with a
   300 s timestamp window and `event_id` idempotency, `PATCH …/update-status/` for manual
   decisions with `nodes_to_resubmit`, presigned short-lived media URLs. We adopt the literals and
   the decision shape verbatim so the console, exports and the site facade need no translation.
9. **Didit's MCP is a remote OAuth endpoint, not an npm package.** [documented]
   `https://mcp.didit.me/mcp`. The export uses REST with an API key (scriptable, no browser
   dance); MCP is optional. Media URLs in decisions expire in minutes, so JSON and media are
   pulled in the same pass.
10. **Lists are real and small.** [measured] User blocklist 1, IP blocklist 2, Document blocklist
    1, custom "High Risk Countries" 35, everything else 0. Migration is trivial; the feature is not.
11. **No vendor has a government check for California licences.** [documented] Didit's base ID check is document forensics (barcode + print cross-check, per-state templates, screen-replay and photo-substitution detectors); its Database Validation add-on covers Latin America/Spain and US credit-bureau headers, not the DMV. AAMVA's DLDV is the only DMV-backed check in the US and **California blocks DLDV access to its own data**. Our engine therefore competes on the same evidence Didit uses, plus multi-frame tilt capture ("document liveness": colour-shifting ink and ghost image must move) that Didit's standard flow does not do. Modern fake IDs carry correct PDF417 barcodes, so barcode agreement is necessary, never sufficient. Source: `scratch/idv-authenticity-research-2026-09-08.md`.
12. **California Civil Code § 1798.90.1 limits retention of scanned licence data** [documented] to what is needed for verification (about 24 h) absent consent, and the CPRA treats a face template as sensitive personal information. The consent-then-keep design in §0 follows from this; DCC 4 CCR § 15404 itself requires only visual inspection.
13. **Open-source liveness is the honest weak point.** [documented, see §2.3] No open PAD model is
    ISO 30107-3 certified. The plan compensates with a server-nonce active challenge, screen-flash
    reflection, capture-path integrity signals, 1:N face search and analyst review, and labels the
    passive score as "open model, uncertified" on the session detail rather than pretending.

### 2.4 How the system decides on its own (the autonomy design)

The engine never emits a bare verdict. It emits a **risk score with capped confidence** and a
list of reasons; the rules turn that into one of three things, in under 3 s from upload:

1. **Approve** — every required signal present and above its threshold, no list hit, no hard signal.
2. **Ask the guest to fix one thing** (`Awaiting User`) — a signal is weak *because of the
   capture* (glare, blur, dark, face too small, card tilted, barcode unreadable, challenge not
   completed). The page shows exactly one sentence and re-opens only that step. Three tries per
   step. This is the "step-up" the census says is mandatory; the person doing the step-up is
   the guest, with a specific instruction, not an analyst.
3. **Decline with a path** — a hard signal (blocklist hit, expired, under age, injection,
   nonce mismatch), or tries exhausted. Online: "Bring your physical ID to any Hyperwolf store".
   In store: the associate holding the card may override with a one-line reason, recorded.

Score caps: whenever a signal is missing (barcode unreadable, PAD unavailable, no face on the
document) the maximum achievable score is capped below the approve line, so a degraded path can
never produce a full-confidence pass. Missing-but-optional signals (ghost portrait, age estimate,
fingerprint blocked) carry no penalty. Lists refresh stale-but-served with an alarm at 24 h.

Because the census shows open recapture/forensics detectors sit near coin-flip cross-domain, the
things that actually stop fraud in this design are: the barcode↔print↔portrait↔selfie chain
(a forged card must be consistent across all four), the ghost-portrait match, the nonce-bound
challenge, 1:N face reuse and ID-number reuse across every session we have ever run, retry and
device velocity, and the physical inspection at the door that California requires anyway.

### 2.5 Calibration without training (the imported Didit history is the asset)

Didit's export gives us ~7,800 sessions with a document portrait, a selfie and a vendor decision.
That is a labelled calibration set, not training data: genuine pairs (same session) and imposter
pairs (cross-session) produce **our own ROC** for SFace and dlib, so the 1:1 and 1:N thresholds
in `idv_workflows.config` are measured on Hyperwolf's real customers and cameras, with the
false-match and false-non-match rates printed next to the slider in the workflow builder. The
same set calibrates the OCR fuzzy-match tolerance per field and the quality gates. This is the
single most valuable thing the migration does and it is why media is imported, not just fields.
Consent for this secondary use is part of the Terms insert (§11.7).
## 3. Data model

All tables live in wm-demo's SQLite (`store.py` migration block `IDV_SCHEMA`), prefix `idv_`.
Timestamps are ISO-8601 UTC text; money is integer cents; JSON columns hold Didit V3 shapes
verbatim so an exported session is byte-comparable to Didit's. Every table that can be written by
an analyst has a matching `idv_audit` row (§3.9). Nothing is ever deleted by `DELETE` except
through the deletion pipeline (§3.10); soft-delete columns are `deleted_at`.

### 3.1 Workflows

```sql
CREATE TABLE idv_workflows (
  id TEXT PRIMARY KEY,                 -- uuid
  name TEXT NOT NULL,
  kind TEXT NOT NULL DEFAULT 'KYC',    -- KYC (KYB reserved)
  version INTEGER NOT NULL DEFAULT 1,
  features TEXT NOT NULL,              -- JSON array, Didit enums: OCR, LIVENESS, FACE_MATCH, AGE_ESTIMATION, IP_ANALYSIS, QUESTIONNAIRE, PHONE_VERIFICATION, EMAIL_VERIFICATION, NFC (declared-unsupported), AML (declared-unsupported)
  config TEXT NOT NULL,                -- JSON: {face_liveness_method:'PASSIVE'|'ACTIVE_3D'|'FLASHING', thresholds:{liveness_min, face_match_min, doc_quality_min, age_rule:'REC_21'|'MED_18_CARD'}, allowed_document_types:[], allowed_countries:[], out_of_state:'allow'|'review', duplicate_person:'review'|'decline', ip:{tor:'decline',hosting:'review',vpn:'review'}, resubmission_max:3, liveness_attempts_max:3, expires_after_days:365, session_ttl_minutes:60, questionnaire_id}
  status TEXT NOT NULL DEFAULT 'active',   -- active|archived
  created_by TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE idv_workflow_versions (workflow_id TEXT, version INTEGER, features TEXT, config TEXT, created_at TEXT, PRIMARY KEY (workflow_id, version));
```
Rules:
- A session pins `workflow_id` + `workflow_version`; editing a workflow writes a new version row and never rewrites a finished session's rules.
- Features the engine cannot run (NFC, AML, DATABASE_VALIDATION, PROOF_OF_ADDRESS) are selectable only as **declared-unsupported** and the builder shows "Not available on the Hyperwolf engine" where the toggle would be. They are stored so an imported Didit workflow round-trips.

```sql
  blaze_member_id TEXT, hw_identity_id TEXT,   -- link to existing hw_identities (reuse, do not copy)

```
Rules:
- 1:N face search is a brute-force cosine over `idv_face_templates` (numpy in the engine, plain

### 3.3 Sessions, events, decisions

```sql
CREATE TABLE idv_sessions (
  id TEXT PRIMARY KEY, session_number INTEGER UNIQUE,   -- monotonic, shown as #N like Didit

  store_id TEXT, associate_id TEXT,    -- POS channel only
  engine TEXT, engine_job_id TEXT,     -- 'hw-engine/<version>' or 'didit' (imported)

  resubmit_nodes TEXT,                 -- JSON, mirrors resubmit_info.nodes_to_resubmit
  review_reasons TEXT,                 -- JSON array of reason codes that put it In Review
  created_at TEXT NOT NULL, started_at TEXT, completed_at TEXT, expires_at TEXT, updated_at TEXT NOT NULL,
  imported_from TEXT, imported_session_number INTEGER, deleted_at TEXT, deletion_instruction TEXT
);
CREATE TABLE idv_session_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT, session_id TEXT NOT NULL,
  event_id TEXT NOT NULL UNIQUE,       -- idempotency key (engine callback / Didit replay / analyst action)
  type TEXT NOT NULL,                  -- status.updated|data.updated|media.uploaded|liveness.attempt|review.action|import
  status_from TEXT, status_to TEXT, source TEXT NOT NULL,   -- engine|analyst|system|website|pos|didit-import
  payload TEXT, received_at TEXT NOT NULL, signature_ok INTEGER NOT NULL DEFAULT 1
);
CREATE TABLE idv_decisions (
  id TEXT PRIMARY KEY, session_id TEXT NOT NULL, version INTEGER NOT NULL,   -- one row per (re)computation
  status TEXT NOT NULL, computed_at TEXT NOT NULL, engine TEXT NOT NULL, engine_version TEXT,
  id_verifications TEXT, liveness_checks TEXT, face_matches TEXT, ip_analyses TEXT,
  age_estimations TEXT, questionnaire_responses TEXT, warnings TEXT, reviews TEXT,   -- Didit V3 arrays verbatim (JSON)
  crosschecks TEXT,                    -- our addition: barcode↔OCR↔portrait field agreement, name↔expected_details, dob↔age rule
  -- scalar mirrors for the table/filters (denormalised from the JSON, never edited directly)
  first_name TEXT, last_name TEXT, date_of_birth TEXT, document_type TEXT, issuing_state TEXT, issuing_country TEXT,
  expiration_date TEXT, document_number_hash TEXT, liveness_score REAL, face_match_score REAL, ip_risk_score REAL, age_estimate REAL,
  UNIQUE (session_id, version)
);
```
Rules:
- **The webhook/callback is the source of truth.** The capture client never sets a status. The
  engine's signed callback (§4.4) and analyst actions are the only writers of `status`.
- `event_id` is unique; a replayed callback or replayed Didit webhook returns 200 and writes
  nothing (the same rule the Bounty money marker needed and lacked).
- `document_number_hash` = sha256 of `issuing_state|document_number` (reuses
  `verify.doc_hash`), so it is comparable with `hw_identities.gov_id_hash` and the document
  blocklist without storing the number in a filterable column. The number itself lives only inside
  `id_verifications` JSON.

### 3.4 Status machine (Didit literals, case-sensitive) — autonomous

There is no analyst step in the normal path. `In Review` exists for Didit parity and for the
in-store override, but the engine never parks a session there waiting for a person: every
uncertain result becomes `Awaiting User` with a guided fix, and after `liveness_attempts_max` /
`resubmission_max` tries the session ends `Declined` with a reason the guest can act on ("try in
store with your physical ID"). Support can overturn a `Declined` later (audited, admin).

`Not Started` → `In Progress` (first media upload) → `Awaiting User` (engine needs another step:
liveness retry, back of card) → `In Review` | `Approved` | `Declined` (engine decision) ·
`In Review` → `Approved` | `Declined` (support, or the in-store associate override) · `Awaiting User` → `In Progress`
(guest redoes the weak step; the engine picks the step and the copy) · `Resubmitted` (a support-issued
new link) → `In Progress` · `Not Started`/`In Progress`/`Awaiting User` → `Abandoned` (client closed, reported
by the capture page) or `Expired` (TTL sweeper) · `Approved` → `Kyc Expired` (sweeper at
`kyc_expires_at`) · `Declined` is terminal except analyst override to `Approved` (audited, needs
`admin`).
Reason codes (stored, shown, filterable). Each maps to a guest-facing fix line in `idv_rules.GUIDANCE` (e.g. `DOC_QUALITY_LOW` → "There's glare over the seal — tilt the card away from the light and try again"). Retryable → `Awaiting User`; exhausted or non-retryable → `Declined`: `LIVENESS_LOW`, `LIVENESS_FAILED_3X`,
`FACE_MATCH_LOW`, `DOC_QUALITY_LOW`, `BARCODE_OCR_MISMATCH`, `NAME_MISMATCH_EXPECTED`,
`DUPLICATE_PERSON`, `IP_HOSTING`, `IP_VPN`, `AGE_ESTIMATE_UNDER_MARGIN`, `OUT_OF_STATE`,
`DOC_NEAR_EXPIRY`, `ENGINE_UNAVAILABLE_MANUAL`, `OVI_SHIFT_NOT_SEEN` (document liveness: colour-shift/ghost did not move across tilt frames), `SCREEN_REPLAY_SUSPECTED`. Auto-`Declined` codes: `DOC_EXPIRED`, `UNDER_AGE`,
`FACE_BLOCKLIST_HIT`, `DOCUMENT_BLOCKLIST_HIT`, `USER_BLOCKLIST_HIT`, `IP_TOR`,
`INJECTION_DETECTED`, `CHALLENGE_NONCE_MISMATCH`, `LIVENESS_ATTEMPTS_EXHAUSTED_HARD`.

### 3.5 Documents and media

```sql
CREATE TABLE idv_documents (
  id TEXT PRIMARY KEY, session_id TEXT NOT NULL, person_id TEXT,
  document_type TEXT, issuing_country TEXT, issuing_state TEXT, document_number_hash TEXT,
  date_of_birth TEXT, expiration_date TEXT, date_of_issue TEXT,
  barcode_fields TEXT, ocr_fields TEXT, mrz TEXT, crosscheck TEXT,   -- JSON
  front_media_id TEXT, back_media_id TEXT, portrait_media_id TEXT,
  quality_front REAL, quality_back REAL, created_at TEXT NOT NULL
);
CREATE TABLE idv_media (
  id TEXT PRIMARY KEY, session_id TEXT NOT NULL, person_id TEXT,
  kind TEXT NOT NULL,        -- document_front|document_back|selfie|selfie_frame|liveness_video|portrait_crop|challenge_frame|import_pdf
  mime TEXT NOT NULL, bytes INTEGER NOT NULL, sha256 TEXT NOT NULL, width INTEGER, height INTEGER,
  storage TEXT NOT NULL,     -- 'disk' (IDV_MEDIA_DIR) | 's3' (AWS port)
  path TEXT NOT NULL,        -- relative, never a URL
  captured_at TEXT, uploaded_by TEXT, source TEXT NOT NULL,   -- capture|pos|didit-import
  retention TEXT NOT NULL DEFAULT 'purge_24h',   -- 'purge_24h' | 'until_customer_deleted' (set when consent is recorded)
  purge_after TEXT, deleted_at TEXT
);
```
Rules:
- Bytes are written to `IDV_MEDIA_DIR/<yyyy>/<mm>/<media_id>.<ext>` with mode 0600; the row is
  written after the fsync. Serving is one route (§4.6) that forces the stored `mime`
  (allow-list `image/jpeg`, `image/png`, `image/webp`, `video/webm`, `application/pdf`), sets
  `X-Content-Type-Options: nosniff`, `Content-Disposition: inline; filename=...`, and requires a
  console role. Nothing uploaded is ever served as HTML (last night's blocker).
- Upload admission: ≤ 8 MB per image, ≤ 25 MB per liveness clip, MIME sniffed from magic bytes
  not the header, EXIF stripped by re-encoding in the engine before the portrait crop is kept.
- At-rest encryption is the volume's job (Render disk / S3 SSE-KMS); wm-demo is stdlib-only and
  will not pretend to encrypt. This is stated on the Retention screen.

### 3.10 Retention, consent and deletion

```sql
CREATE TABLE idv_consents (id TEXT PRIMARY KEY, session_id TEXT NOT NULL, person_id TEXT, kind TEXT NOT NULL /* terms|biometric_retention */, terms_version TEXT NOT NULL, terms_url TEXT NOT NULL, accepted_at TEXT NOT NULL, ip TEXT, user_agent TEXT, withdrawn_at TEXT);
```
Rules: a session's media is created with `retention='purge_24h'` and `purge_after = created_at + 24h`;
when a `biometric_retention` consent row is recorded for the session (the guest ticks the specific
box, terms clickable on the same screen) the media and the face template flip to
`until_customer_deleted`; the sweeper purges expired media hourly and writes an audit row. Withdrawal
purges within 24 h and keeps the decision and hashes. The terms version shown is stored with the
consent, and the demo's capture screen and Settings → Retention both print: "Update the Hyperwolf
Terms and Conditions to cover Civil Code 1798.90.1 before this goes live."

```sql
CREATE TABLE idv_deletion_requests (id TEXT PRIMARY KEY, target_type TEXT NOT NULL /* person|session */, target_id TEXT NOT NULL, instruction TEXT NOT NULL /* operational_session_delete|privacy_erasure */, retain_face_template INTEGER NOT NULL DEFAULT 0, requested_by TEXT NOT NULL, requested_at TEXT NOT NULL, executed_at TEXT, outcome TEXT);
```
Rules: deleting a customer (person) deletes every session's media files, decisions' JSON PII,
documents, face templates (unless the request retains the template for blocklist purposes,
Didit's `retain_face_embeddings`), and leaves tombstone session rows with `deleted_at` so
counts and audit stay truthful. Two-step: request, then execute (admin), both audited.

### 5.5 Capture flow specifics
- `getUserMedia` with rear camera preference for documents, front for selfie; guides drawn on a
  canvas; client-side blur/glare hints are advisory (server decides).
- Consent first: one screen, terms clickable, the specific retention/biometric box unbundled; declining the box still allows verification (24-hour purge).
- Document: front with a short tilt (3–5 frames while the guest rocks the card, so colour-shifting ink and the ghost image can be seen to move), then back (PDF417 required for US DL/ID; the page says why).
- Selfie: 2 s of passive frames, then the challenge script from the server (nonce shown as a
  colour/flash sequence and head-turn prompts), recorded as WebM (or a frame burst where
  `MediaRecorder` is missing), uploaded with the challenge id.
- Any weak step: the engine returns `Awaiting User` with one reason and the page shows the fix in
  one sentence ("Move somewhere brighter and look straight at the camera"), re-opens only that step,
  and targets under 3 s from upload to answer. Up to 3 tries per step, each an event with its
  score; then `Declined` with the reason and the path ("Bring your physical ID to any Hyperwolf
  store — the associate can verify you there"). A hard signal (`INJECTION_DETECTED`,
  `CHALLENGE_NONCE_MISMATCH`) declines immediately and the page says so without detail. Nothing
  passes silently; nothing is dropped; nothing waits for a person.
- Abandon: `visibilitychange`/`pagehide` beacon; TTL sweeper expires stale sessions.
- POS channel: `IdvCapture` inside the check-in modal via the seam file; the associate sees the
  live status and the engine decision. On `Declined` the associate, who is holding the physical
  ID, may override on the spot: a required one-line reason, recorded as a review row and an audit
  row, tier T1-manual, re-verified next visit. Online has no override.

## 6. Roles and identity (and the production gap)

`HWIdv.session()` returns `{id, name, role, storeId}` from `window.HW.STATS.associate` with the
same fallback identity as Bounty. Roles for Verify: `viewer` (read), `analyst` (approve, decline,
resubmit, notes, assign, edit data), `admin` (workflows, lists, keys, webhooks, team, deletion,
override Declined). The backend maps `X-HW-Actor` to a role via `associates` and refuses writes
without it (`403 {"error": "..."}`) — the role check that Bounty's manager-only writes lacked.
There is no login in the estate; the Team screen says so in one line. If the owner needs real
console authentication for PII access before this ships, that is a platform decision (§11.5).

- `python3 qa/battery.py --suite idv` green on a scratch DB: schema, status machine (every

  gates (viewer cannot approve; analyst cannot override Declined), deletion completeness, import
  invariant, dashboard sums equal table sums for the same filter.
- Engine: `/engine/v1/health` reports real model names and versions; a fixture set (own photos

  printed photo and a phone-screen replay fail liveness; a wrong challenge nonce declines.
- Live on a fresh port nobody used this session: all 14 routes render loaded/empty/error, the
  header badge distinguishes backend-down from engine-down, a session created through
  `/v3/session/` with a real key completes through the hosted page and appears in the table

## 9. Risks and how the design absorbs them

| Risk | Handling |
|---|---|
| Open-source passive liveness misses a good replay attack | Active challenge bound to a server nonce, flash-reflection check, capture-path integrity signals, 1:N search against prior sessions and the face blocklist, and `In Review` on any low-confidence score. The score is labelled uncertified; the workflow can require `ACTIVE_3D` for every session. |
| Model weights with non-commercial licences | The census (§2.3) lists licences per model; only commercially usable weights are in the default stack; the engine's health endpoint prints each model's licence so it cannot drift silently. |
| Engine container too heavy for Render Pro | CPU-only ONNX exports, lazy model load, image ≈ 2–3 GB; measured at build, reported in `IDV-STATUS.md`; the AWS port can use a larger box. |
| PII on a Render disk | Volume encryption is the host's; the app enforces role-gated media, no-store caching, audit per view, mode-0600 files, and a documented deletion pipeline. Stated plainly on the Retention screen. |
| Same-origin media served as HTML (last night) | One media route, forced MIME from the row, magic-byte sniffing at upload, `nosniff`. Probe included. |
| Site lets `In Review` through | Facade returns the literal; escalation §11.2 decides whether the site changes. |
| Duplicate people / name mismatch | `identity_match.py` tiers + face 1:N produce `DUPLICATE_PERSON` / `NAME_MISMATCH_EXPECTED` review reasons; merging is an audited analyst action. |
| Webhook replay / callback forgery | HMAC + 300 s window + `event_id` unique index; replay returns 200 and writes nothing. |
| Long-running import against Didit rate limits | 600 GET/min; importer paces at 300/min, checkpoints `cursor_after`, resumes; media pulled in the same pass because URLs expire. |
| Bandwidth on Render | Poll short-circuit on `idv_version`, backoff when the tab is hidden, thumbnails generated once at upload. |
| Register screen rule | Integration through a new seam file and the check-in modal's existing hooks; `screen-register.jsx` untouched (grep gate). |

## 11. Escalations (not built without a ruling)

1. **Which Didit workflow is the production one to mirror?** The console's newest sessions are
   "Hemp Verification (no selfie)"; you said cannabis + selfie. The default workflow seeded on
   day one will be "Cannabis Verification + Selfie" (OCR, IP, passive liveness, face match,
   age rule REC_21) unless you say otherwise.
2. **"In Review" completes checkout on the site today.** Keep (fast checkout, review after) or
   fix (site waits for Approved)? The facade returns the literal either way.
3. **Engine down at the register.** Decided in principle by "depends on the channel": the
   associate holding the physical ID may record a manual check (tier T1-manual, re-verified next
   visit). Confirm that the same override applies when the engine is unreachable, not only after
   a decline.
4. **Medical 18+ rule source.** The engine can verify age; it cannot verify a medical card. Which
   system says a customer is medical (Blaze member flag via `expected_details`, or a card photo
   step reviewed by an analyst)?
5. **Console authentication for PII.** Verify shows document images to anyone who can open the
   page in this estate. If that is not acceptable before the demo is shown outside the company,
   real auth is a platform decision, not a module one.
6. **Deleting Didit history after import.** The importer never deletes at the source. Batch
   deletion at Didit (privacy erasure) is a separate, irreversible step for you to trigger.
7. **Terms and Conditions update.** The consent design depends on the Terms covering Civil Code § 1798.90.1 and biometric retention; `docs/IDV-TERMS-CLAUSE-DRAFT-2026-09-08.md` is a draft for licensed counsel, not legal advice. Nothing ships to real guests before counsel signs it off.
8. **Blocklisting a person** is a judgement about a person: the console supports it; the default
   lists start with the four imported entries and nothing is auto-added except device/IP
   signals flagged as `INJECTION_DETECTED`, which land on a *custom* "suspect devices" list for
   review, not on a blocklist.
