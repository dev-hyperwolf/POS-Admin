# Legacy data model inventory — the twelve Hyper-Tech repos, 2026-09-17

Purpose: give `platform/sync` (the Mongo -> Postgres sync tool being built in parallel under
`/Users/jt/wm-demo/platform/sync/`) a complete, cited map of every Mongoose model across the
twelve production repos cloned read-only under `/Users/jt/hyper-tech`, so its mapping files
(`/Users/jt/wm-demo/platform/sync/mappings/*.json`) can be written and reviewed against real
field names rather than rediscovered from scratch.

**Read before this doc**: `/Users/jt/POS-Admin/docs/codebase-audit/README.md` (index),
`CANONICAL-DATA-MODEL.md` (the reconciled cross-repo model this doc treats as background, not
duplicated here), `ARCHITECTURE-MAP.md`, and `metrics/CROSS-REPO-DUPLICATES.md` (the mechanical
near-duplicate-file detector this doc's Duplicates section leans on). This doc adds the lenses
that prior audit did not carry: PII classification per field group, money unit (dollars vs.
cents, not just "money"), `Mixed`/untyped fields, embedded arrays as child-table candidates, and
a straight read/write-repo count per collection.

**Method**: `docs/codebase-audit/metrics/*.json` (`tools/hw_audit_metrics.py`'s mechanical output)
supplied the field/index/timestamp counts for all 252 Mongoose model declarations across the
seven backend repos (the five frontend/admin repos — `hemp-frontend-nextjs`, `hemp-retailer-admin`,
`hyperwolf-frontend-nextjs`, `hyperwolf-super-admin`, `stilo-frontend-nextjs` — have zero Mongoose
models; they hold client-side type beliefs and Redux state instead, already catalogued in
`docs/codebase-audit/repos/*.datamodel.md` and not repeated here). Five parallel read-only research
passes then read every one of those 252 schema files directly (not just the prior audit's prose) to
classify PII, money units, `Mixed`/untyped fields, embedded arrays, refs, and soft-delete
conventions field-by-field, cross-checking against the prior audit's `repos/<repo>.datamodel.md`
and `CANONICAL-DATA-MODEL.md` rather than trusting either blindly. **No `.env` file, credential
file, or database connection was read or opened at any point** — every finding below comes from
static reads of `.js` schema source. Where a config file elsewhere in a repo holds a connection
string, this doc names the file and the variable, never the value (none needed to be, since no
mapping below required reading one).

Two rows short of 252: `promotion-engine` has no Mongoose schema at all (confirmed:
`grep -arn "mongoose.Schema\|new Schema("` across the whole repo returns zero hits) — it reads and
writes `promotion-backend`'s own `promotions` collection via the native MongoDB driver; see the
narrative at the end of the table instead of two rows for it. `PromoCode`/`Rule` in
`promotion-backend` and `Miscellaneous` in four repos were each declared twice in the raw
mechanical census (duplicate metrics-tool entries pointing at the same file) and are collapsed to
one row here.

## Conventions found across all twelve repos (see `CANONICAL-DATA-MODEL.md` §0 for the full writeup)

- **Ids**: Mongo `_id` ObjectId plus an application string id (`memberId`, `productId`, `orderId`,
  `storeId`, `regionId`, `fleetDisplayId`) generated by `Math.random()`, `mongoose-sequence`, or
  copied from Blaze. Joins in application code use the string id, not `_id`.
- **Money**: bare `Number`, assumed dollars, no `Decimal128`, no cents anywhere in any of the 252
  models read for this pass. Every `unit` value in the table below marked `unknown` or `dollars`
  is this pass's best inference from field name and the estate-wide convention documented in
  `CANONICAL-DATA-MODEL.md` §0 — **none of it was re-verified against live sampled values**, which
  this task's hard rules forbid (no database connections). Treat every `dollars_to_cents`
  transform in the mapping files as provisional until spot-checked against real data.
- **Time**: `createdDate`/`updatedDate` as epoch-ms `Number` (the majority convention) or a real
  `Date` (hyperdrive-backend, distribution-backend's `conn3`-adjacent models, promotion-backend).
  `timestamps: true` appears on exactly one model across all 252: `promotion-backend/PromoCode`.
- **Tenant key**: `retailerId` (hemp), `storeId` (stilo), a `platform` enum
  (`hyperwolf|hemp|stilo`, distribution/promotion), or which Mongo connection a model is registered
  on (`conn1`/`conn2`/`conn3`, hyperwolf/promotion-backend) — client-supplied, unindexed, never
  derived from the authenticated caller.
- **Soft delete**: present on roughly 5% of the 252 models, in at least five different shapes:
  `isDeleted: Boolean` + `deletedBy` ref (Fleets, all three repos), `isActive: Boolean` (most
  hyperdrive/distribution config/reference models), a `status: Boolean` used as an active flag
  (roughly 40 hemp/stilo content and catalog models), a `status: String` enum
  (`Active`/`Inactive`, a smaller set of the same models — inconsistently typed against the
  Boolean convention on sibling models), and `deletedAt`/`deletedBy` timestamp pairs (hyperdrive's
  `Announcements`/`FailureReason`). No model in any repo uses a single consistent convention.
- **Auth secrets**: `Admin`/`Store`/`StoreUser`/`Employee`/`Fleets` all store a password field
  directly on the model (`password`/`fleetPassword`/`pin`), and `Admin.generateAuthToken()`
  (hemp-backend, `models/Admin.js:21`) signs a JWT with `process.env.JWT_ADMIN_PRIVATE_KEY` — the
  variable NAME only; its value was never read for this pass, per this task's hard rules. The same
  variable name is reused across at least three repos per `CANONICAL-DATA-MODEL.md` §1.2, meaning
  a token minted by one repo's `Admin` model may validate against another's.

## Full model census (246 rows, one per Mongoose collection)

Columns: **Fields** = declared schema field count (`tools/hw_audit_metrics.py`'s mechanical count,
top-level only — nested sub-document fields are not double-counted here but are listed under
Embedded arrays / Mixed where relevant). **PII** groups fields into `personal` (name, email, phone,
address, DOB, a non-verification photo) and **restricted** (government ID/license, SSN-class,
payment/bank detail, medical record, plaintext password/PIN, biometric or verification imagery) —
bold marks restricted. **Money fields (unit)** lists every field this pass judged monetary, with
its inferred unit (`dollars`/`cents`/`unknown` — see the money convention note above; a field
proven negative-capable, e.g. a margin or refund, is noted in the mapping file that consumes it,
not here). **Mixed/untyped** = `mongoose.Schema.Types.Mixed`, a bare untyped `Object`, or a bare
untyped `Array` with no item schema. **Embedded arrays** flags arrays of embedded sub-documents
that should become child tables in Postgres, with their sub-fields where known. **Refs** lists
`ObjectId` references found, including ones this pass could show are dangling/broken (the target
model name does not exist under that name in the repo). **Soft-delete** names the field/convention
if any exists on that model, else `-`.

## `promotion-engine` — the one collection with no Mongoose model

`promotion-engine` reads and writes `promotion-backend`'s `promotions` collection (the
`Promotion` row above) via the native MongoDB driver, with no schema of its own anywhere in the
repo (confirmed zero hits for `mongoose.Schema`/`new Schema(`). Fields as this repo actually uses
them: `_id` (compared via `.toString()`), `code` (`Array<string>`, first non-empty is canonical,
`utils/promotion-helpers.js:8-25`), `status` (string, only `"active"` is ever checked — this
repo's own `core/constants.js:189-195` declares 5 enum values against the writer's real 2-value
enum, so 3 of 5 can never occur), `platform` (string or `string[]`, both shapes tolerated
defensively), `autoApply`/`isIndividualUsed` (booleans), `usageLimit`/`usageLimitPerUser`
(numbers, `<=0`/non-finite means no limit), `promoUsage` (number, `$inc`'d in
`controllers/promotion-controllers.js:414-417`, legacy fallback field `codeUsage`),
`timezone`/`timeMode` plus the triple-aliased `publishDate|scheduledDate|startDate` /
`expiryDate|expireDate|endDate` (first non-null wins), and `rules.ifRules`/`rules.thenRules`
(`Mixed`-shaped, structure varies by rule type, recompiled fresh every request via
`engine.js:1270-1284`). Top-level `rule`/`actions` are write-only from this repo's own
perspective — `promotion-backend` writes them after calling `/compile-promotion`, but
`promotion-engine`'s live evaluation path never reads them back. No PII in this collection.

## Ten riskiest fields (type ambiguity, float money, PII)

1. `Member.idImage` (hemp-backend) / equivalent on stilo/hyperwolf's `BlazeUser` — a government ID
   photo URL, documented **public-read on S3** in production (`CANONICAL-DATA-MODEL.md` §1.1).
   `encrypt_pii` on the column does nothing if the underlying object is still public-read.
2. `Discrepancy.discrepancyAmount` (distribution-backend) — typed `String`, not `Number`, despite
   holding a cash amount used in a cash/inventory reconciliation workflow.
3. Every `productPrice`/`unitPrice`/`salePrice`/`purchasePrice`/`totalPrice`/`margin` field across
   all Product-family models (hemp/stilo/hyperwolf/distribution/promotion-backend, ~15 fields) —
   bare `Number`, dollars assumed from convention only, never independently verified against live
   data (this task's hard rules forbid a DB connection to check).
4. `stilo-backend:Tax.taxes[].taxRate` — unclear whether it is a percent (`15`), a fraction
   (`0.15`), or already basis points; `tax_rates.rate_bps` (the one REAL target table in this
   inventory) needs whichever conversion is right, and guessing wrong silently mis-taxes every
   order once live.
5. `Admin.password` / `Store.password`+`PIN` / `StoreUser.password`+`pin` / `Fleets.fleetPassword`
   — plaintext-field-named secrets shared across a single `JWT_ADMIN_PRIVATE_KEY` signing secret
   estate-wide (variable name only, per this task's rules); every mapping in this pass drops these,
   never copies them.
6. `BlazeUser.userData` (hyperwolf-backend) — untyped Object holding "the whole Blaze member" per
   `CANONICAL-DATA-MODEL.md` §1.1; may itself contain payment or ID data Blaze stores, unverified.
7. `Order.canpay_transaction_id`/`canpay_intent_id` family (hyperwolf/distribution) and
   `creditCardDetails` (hemp/stilo/hyperwolf ActiveCart+Order) — live payment-gateway identifiers
   and card data sitting in an application database, not just a payment processor.
8. `KitDistributed` (distribution-backend, 63 fields) — 4 levels of array nesting
   (`regionData[]`->`items[]`->`refillLogs[]`->`productBatches[]`/`productBatchesBlaze[]`); any
   naive flattening risks silent data loss or an explosion of child tables.
9. `HempProducts.inventories[]` / `StiloProducts.inventories[]` / equivalent — no natural per-row
   id or compound unique key declared; this pass's mapping assumes at most one row per region per
   product, which held in sampled prior-audit examples but is not schema-enforced.
10. `Order.items[].productId` (hemp-backend) and equivalents — a plain `String`, not a Mongoose
    `ref`, assumed to line up with the matching Product collection's own external id field; never
    cross-checked against sampled data (forbidden: no DB connection).
