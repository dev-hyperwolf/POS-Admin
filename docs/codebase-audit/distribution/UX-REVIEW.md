## 2. Core journeys

**(a) Build and dispatch this week's kits** — Regions (confirm today's driver-to-subregion assignments via "Assigned Driver Today," `updateAssignedSubRegion.jsx:113` — a subregion missing today's assignment simply won't be selectable later, with nothing on the template screen pointing back here to explain why) → Kit Template (create, then Assign Products on a second page — setting Min/Max Qty per SKU with no visibility into current stock, see finding #2b) → on any edit-mode save, a mandatory "Planner Override Notes" modal appears (`plannerOverrideNotes.jsx`) whose note is **not actually required** to submit (no empty-check in `handleSave:30`) and whose only escape (the X icon, Cancel is commented out) **silently discards every pending product/box/quantity edit with no warning** → Distribution Management → "Distribute" (`SelectRegionModal`, one click commits `addDistributionManagement`, no preview of what will actually be placed) → Distribution Details (review result, Low-Stock drawer scoped only to "box limitation") → Freeze (`freezeDistribution.jsx`, button says "Yes, Distribute", never mentions the Blaze sync it's actually gating — a `syncBlazeInventory` call is commented out at `:37`). Minimum 6 screens, 4 modals, ~20-25 clicks for one distribution. **Hidden failure**: the backend's round-robin/all-subregions-or-nothing placement (`manageDistributions.repository.js:722,745,770-775`) runs invisibly — no screen ever says "N units of SKU X didn't fit any subregion and were skipped." **State in the operator's head**: whether every subregion actually got each SKU, whether "Freeze" has propagated to Blaze (nothing in the UI confirms it did), and — while setting Min/Max Qty in the template — what the current on-hand stock actually is, since that number lives only on a different screen (Boxes→Products or Box Details). **Same fact, different screens**: "Total Product Quantities" on the list vs. "Total Qty By Region" in Distribution Details come from different endpoints with no shared client cache (only 21 of 124 thunks touch redux state) and were never cross-verified.

**(b) Run today's refill** — Kit Refill Logs → "Refill Kit" (`SelectRegionModal`, one click commits `createRefillKit`, zero preview — `testRefillKit` exists but is dead code) → result appears on the list as Kit Value/Refill Qty only → drill into Refill Details for per-subregion Distributed/New/**Sold** Qty and the one skip signal in the whole family (Low-Stock drawer, "box limitation" only). None of the three real defects named in the backend audit — ASAP-only sold filter, permanently-lowered cap, alphabetical new-product gate — produce any visible signal anywhere in these six screens; `cap`/`usedQty` is never shown. To correct a bad refill the only tools are `addProductRefill` (single-SKU manual add, safe-inventory check **commented out**) or bulk edit — both blind to why the automatic pass got it wrong.

**(c) Scan a driver's kit at pickup** — confirm the global Scanning toggle → Driver List (search) → Driver Kit Details: an invisible hidden barcode input with no "ready to scan" indicator; each scan emits a Socket.IO event with an ack callback and **no timeout/retry** (`driverKitDetails.js:516-527`) — a dropped ack freezes all further scanning silently; success and every failure type (wrong product, over quantity, duplicate) share one of two generic toasts; deleting a mis-scanned row is the only place the PIN modal appears, mislabeled as a plain "Enter Pincode" with no indication it's a supervisor re-auth, not a driver check. No running "X of Y left" counter exists. Leaving the screen silently auto-holds the kit (not on hard refresh/tab close).

**(d) Close a day and resolve a discrepancy** — Closure Forms (separate top-level "Loss Prevention" menu, disconnected from the Distribution build/refill/scan flow) → Region Closure → Details (the `totalInventoryValue` bug is hidden by commenting the column out, not fixed) → Revenue Reconciliation (the one screen with client-side math) → Add Discrepancy → Final Report → Approve (writes into another service's database with no contract test, invisibly to the operator). Separately, Discrepancy Management (Kanban) and Discrepancy Approvals (scan-to-verify, hard-gated, dead note button) are two more, unlinked screens for what is conceptually one discrepancy record.

**(e) Add a newly received premium product so it goes out today** — no screen in the build/refill/box path shows a received-date, purchase-date, or age-in-days field (confirmed by grep: zero hits for `receivedDate`/`purchasedDate`/`agingDays` outside the standalone Aging report, and that report's own "Aging (Days)" column is commented out, `agingProducts/index.js:121-128`). The only way to force a product out today is the one-at-a-time `addProductDistribution`/`addProductRefill` forms, repeated by hand per subregion, with no bulk "distribute this new SKU everywhere now" action and no safe-inventory guard on the quantity field.

## 3. Findings, ranked

1. **No preview before either commit action.** "Distribute" and "Refill Kit" both route through the same `SelectRegionModal` (`distributionManagement/index.js:202-209`, `refillLogs/index.js:148-157`) — pick subregions, Save, the thunk fires immediately. **Cost**: every full build and every daily refill commits sight-unseen; errors surface only later, at closure/discrepancy time. **Fix**: insert a mandatory preview screen between click and commit showing product/sold/cap/need/give (reuse the already-half-built `testRefillKit`/`use/qty` and low-stock calls), requiring a second explicit confirm.

2. **Product age is invisible everywhere it would matter, and the one screen that had it disabled it.** `agingProducts/index.js:121-128` comments out the "Aging (Days)" column entirely; no build/refill/box screen shows a received-date field at all. **Cost**: this is the direct, on-screen cause of "premium stock sits for a week" — staff have no way to see which SKUs are aging without leaving the workflow for a disconnected, action-less report. **Fix**: re-enable `agingDays`, add a "Received (≤N days)" filter chip directly on Assign Products, Boxes, and both add-product forms.

2b. **The kit template's own Min/Max Quantity form is filled in blind to stock, and "days until expiry" is defined in two places with no stated precedence.** The Assign-Products-to-Template grid shows Name/SKU/Category/Brand/Price/Min Qty/Max Qty but no stock/available-quantity column (`assignProducts.jsx:97-197`) — an operator sets caps for a SKU without seeing what's on hand, and would have to separately open Boxes→Products or Box Details to find that number and hold it in their head. Separately, Distribution Config defines a single global "Products Expiring In [N] Days" default (`AddDistributionConfigForm.js:469-483`) *and* a per-category override table, "Aging Rules By Category" (`:606-650`), on the same page, with nothing on screen stating which one wins for a given category. **Cost**: template quantities get set without reference to real stock, and two admins can each believe a different expiry threshold is authoritative for the same category. **Fix**: add a read-only Available Qty column to the template SKU grid; add an explicit "per-category rule overrides the global default" note (or a single merged table) to Distribution Config.

3. **Distribution status is raw unstyled text on the screen that most needs it, while a ready-made colored component for the exact same values sits unused elsewhere.** `distributionManagement/index.js:72-78` prints `status` verbatim with no `cellRenderer`; `common/component/StatusText.jsx:35-46` already maps `splitting`/`freeze`/`distributed` to icon+color+label and is used on 5 other screens (`driverKitVerification/index.js`, `driverList.js`, `regionClosureForms.js`, `discrepancyApprovals/index.js`, `regions.jsx`). A commented-out action-gate (`// data?.status === "Splitting Finished" &&`, line 84) shows the devs once intended to disable actions post-freeze and stopped enforcing it. **Cost**: operators cannot tell at a glance which distributions are still splitting vs. frozen vs. distributed, and can still edit/delete after freeze. **Fix**: swap in `<StatusText/>`; restore the action gate.

4. **The Freeze button's copy says the wrong thing, and the code that would make it true is commented out.** `freezeDistribution.jsx` confirm button reads "Yes, Distribute" though the action only sets status to `freeze`; a `syncBlazeInventory` call is commented out at line 37. Per the backend audit, Blaze's own sync only picks up `freeze` status and nothing in this UI calls it — the actual trigger is an unidentified external cron. **Cost**: operators reasonably believe clicking this button moves product; it does not. **Fix**: rename the button, and either wire the sync call inline with visible progress or add a "Frozen — awaiting sync" banner plus a manual "Sync Now."

5. **Per-region status (pending/dispatched/hold/paused) is shown nowhere.** `distributionManagement/index.js` subregion columns are Regions/Sub Regions/Min-Max only (`:131-169`); `distributionDetails/index.js` exposes only a page-wide `isFreezed` boolean, no per-subregion chip. **Cost**: operators can't tell which subregions are paused/on hold — the exact condition under which the refill's all-subregions-or-nothing gate silently drops a subregion. **Fix**: add a Status column via `StatusText` to the subregion accordion.

6. **Structured failure data is invisible unless one screen happened to be hand-coded for it.** `axiosClientDistribution.js:44-56` passes every HTTP-200 straight through regardless of body content; the shared `showToastMsg` helper (`addRegionKit/index.js:19-39`) extracts only a `message` string; `grep` for `skippedSubRegionIds`/`success` across the whole slice returns nothing. The single exception across all 20+ screens is the Low-Stock drawer on Refill Details, itself scoped to one cause. **Cost**: partial failures (a skipped subregion, a failed Blaze batch) show as a plain success toast or nothing. **Fix**: a shared "partial-success" banner component fed by a structured `{skipped, warnings}` field the backend should return.

7. **"Kit Template" silently stacks two unrelated tables on one route.** `layouts/distributionSetting/kitTemplate/index.js:9-11` renders the distribution-template table then the refill-template table back to back; both share identical columns (`kitTemplate/index.js:45-195` / `RefillTemplatePage.js:45-195`), differ only by a `templateType` filter and heading text, and both "Create Template" buttons resolve to the same route distinguished only by router-navigation state (lost on refresh). "Copy to Refill" (`kitTemplate/index.js:207`) is the only, easily-forgotten bridge between them. **Cost**: an operator fixing "wrong products in kits" can edit the distribution template while believing they fixed the refill template — the two artifacts that separately drive the two symptom-generating processes are visually almost indistinguishable. **Fix**: split into two clearly labeled tabs; show a "last copied / out of sync" indicator per refill template; fold Copy-to-Refill into the distribution template's own save.

8. **"Update Distribution" Save is dead code.** `addDistribution/index.js:107-146` validates the form, then hits `return;` at line 134 — one line before the actual `dispatch(addDistributionManagement(...))` at line 136, which never runs. The route (`.../update-distribution/:distributionId`) is live and reachable (`routes.js:2447-2453`). **Cost**: any edit made here is silently lost, no error shown. **Fix**: delete the stray `return`.

9. **The scan socket call has no timeout and fails silently.** `driverKitDetails.js:516-527` sets `isScanning=true` before `socket.emit('scanProduct', ...)` and clears it only inside the ack callback; the backend never emits unsolicited events (callers doc §3), and nothing times this out. **Cost**: a dropped ack freezes the scanner with zero visible feedback — indistinguishable from a broken device, plausibly the direct cause of under-scanned kits that surface later as unexplained discrepancies. **Fix**: wrap the emit in a client timeout that resets the flag and shows an explicit retry prompt.

10. **Scan success and every failure type share the same two generic toasts.** Success: fixed "Product scanned successfully"; failure: `message || "Something went wrong"` regardless of wrong-product, over-quantity, or already-scanned (`driverKitDetails.js:~533,~558`). Overscans are visible only as a progress-bar color change the operator must notice. **Cost**: mis-scans compound before anyone notices, generating the discrepancies Loss Prevention then has to reconcile. **Fix**: three distinct, reason-coded states.

11. **The Loss Prevention flow is a separate top-level menu, disconnected from the workflow it concludes.** "Inventory Distribution" (`routes.js:2261`) and "Loss Prevention" (`routes.js:2566`) are two independent collapsible groups; nothing links a driver's Kit Report to that driver's same-day Closure Form. **Cost**: staff have to context-switch menus mid-investigation, and the owner's own team apparently doesn't connect refill errors to the closure/discrepancy evidence that would explain them. **Fix**: nest Closure/Discrepancy/Waste as a "Day Close" subgroup under the same Distribution menu; cross-link kit report ↔ closure form.

12. **The manual override forms — the operator's only recourse when the automatic build/refill is wrong — have their one safety check disabled.** The available-quantity guard on `qtyPerDriver` is commented out in the add-product-refill validation. **Cost**: the exact rush-a-premium-product-out-today path has no protection against assigning more units than exist in the safe. **Fix**: re-enable the check.

13. **The `totalInventoryValue` bug was hidden, not fixed.** Both `regionClosureForms.js:106-114` and `details.js:303-306` comment out the "Total Retail Value" column/tile rather than correcting the backend's qty×dollar-total math (`closure-overview-controller.js:993`). **Cost**: operators lose a genuinely useful number instead of getting a correct one, and the underlying bug remains live for any other consumer of that field. **Fix**: fix the backend calculation, then restore the column.

14. **Waste Inventory can look falsely empty with no explanation.** No UI element references `discrepancyResolutionETA`, the backend field that empties the list when unset (`waste-inventory-controller.js:27-37`). **Cost**: "no waste" and "config not set" are indistinguishable, hiding real waste. **Fix**: surface the ETA setting on-screen and show a distinct empty-state message when it's unset.

## 4. What a better design would do for the two reported symptoms

- **A "received in the last N days" lane on Assign Products, Boxes, and both add-product forms** — sort/filter by the `agingDays` field that already exists in the API response and is merely hidden (`agingProducts/index.js:121-128`), so staff can see and prioritize new stock inside the same screens they already use to build and refill kits, instead of a disconnected report nobody checks.
- **A refill/build preview before commit**, listing sold / need / cap / given per product, populated from the same `use/qty` endpoint the dead `testRefillKit` thunk already calls — this turns today's one-click, no-visibility "Refill Kit" and "Distribute" actions into a checkpoint where a wrong quantity or a skipped SKU is caught before it reaches a driver's kit, not after.
- **A skip-reasons panel** that lists every product/subregion the run didn't place and why (box limit, all-subregions gate, ASAP-only sold filter, capped ceiling) — today only one of these four reasons ("box limitation") is ever shown, and only after the fact.
- **One status timeline per distribution/refill** (Splitting → Frozen → Synced → Dispatched → Closed), using the `StatusText` component that already exists and is already used on five other screens — replacing the current pattern of inferring state from which buttons happen to be visible.

Together these turn "the refill put the wrong product in the kit and we found out at closeout" into "the refill preview showed it was about to under-stock SKU X, and staff fixed it before the kits left the warehouse" — addressing both symptoms at the point they're created, not after.

## 5. Recommendation

Keep and fix the screens rather than rebuild the console: the component library, table pattern (`AgGridAccordionTable`), and status vocabulary (`StatusText`) are already coherent and mostly just unused or disconnected, not architecturally wrong. The highest-leverage fixes — enabling the aging column, adding a preview step to the two commit actions, and applying the existing `StatusText`/gating pattern consistently — are small, surgical, low-risk changes to existing files, not a rebuild. A rebuild is worth revisiting only if the backend decision-engine work (logic map §6, option B) also lands, since a new backend contract (sold/cap/skip-reasons as real fields) is a prerequisite for most of these UI fixes to have anything to display.
