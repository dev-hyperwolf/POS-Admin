Mapping Weedmaps delivery listings to our regions

Weedmaps assumes 1 pin = 1 service area = 1 driver. We don't work that way: one WM delivery listing can be served by 3–5 regions, and a single region can sit inside two listings at once (below, SB-02 Ontario and RC-02 Corona are each shared). So the listing→region link can't be a foreign key — it's a many-to-many relationship, and the real fulfilment decision is made per-order, not per-listing. Five ways to model it. All five converge on the same runtime: the Weedmaps Draft webhook hands us the cart + address synchronously, and Hyperdrive picks the one region + driver best able to fill it.

◆ The Draft webhook is the hinge

At checkout WM POSTs the cart to us and waits. We have ~3s to resolve address→region→driver and mutate availability, price and fees before WM commits. This is the only place we can bend WM's 1-pin model — every option leans on it.

◆ Hyperdrive decides, not config

Mapping just defines the candidate set. Which region + driver actually fulfils is scored live by Hyperdrive on inventory fit (does an on-shift kit have the cart?), ETA, and current driver load.

◆ external_id stays sacred

Items sync per SKU via external_id. The advertised WM menu is a union of what candidate regions' on-shift kits carry — the webhook trims it to reality per address.

Follow-up · Option 3
Controlling the Weedmaps menu on the address-first route
Key thing to internalise: Weedmaps shows ONE menu per listing to everyone browsing — you can't vary the browse menu by address before checkout. So "address-first" doesn't mean an uncontrolled menu; it means you control it with three levers instead of a per-region config. Work smarter: publish once, let the live feed prune, let the webhook enforce truth.
1 · What's ON the menu = what we publish

The Menu API (PUT …/items/external/{external_id}) decides which SKUs exist on the listing at all. For address-first, publish the servable superset — the union of every SKU any covered region's kit can carry. That union is the browse menu. Categories, featured items and ordering are set here too.

2 · What's IN STOCK = live kit coverage

Each item's in-stock flag is driven off the live shift + kit feed: available while ≥1 on-shift driver in any covered region carries it, auto out-of-stock the moment coverage hits zero. The menu self-prunes as drivers start and end shifts — a called-off driver's unique SKUs simply drop. No manual curation.

3 · What actually ships = the Draft webhook

The browse menu is a promise to everyone; the per-address truth is enforced at checkout. When WM sends cart + address, we resolve the region and remove or reprice any line the assigned driver can't fill before replying (<3s). Shopper sees one menu; we make it real at the last synchronous step.

What the shopper sees vs. what we control
ABrowse → one flat menu = the published union, minus anything with zero live coverage.
BEnters address at checkout → Draft webhook fires.
CHyperdrive resolves region+driver by inventory, trims the cart to what that driver actually has, reprices, replies.
The one risk — and how it's contained
The only downside of address-first is a browse menu that can over-promise for a specific address. Levers 2 and 3 contain it: live-coverage toggling keeps genuinely-unservable SKUs off the menu entirely, and the webhook catches the address-specific gaps at checkout. For the cleanest shopper experience, only mark a SKU "always on" when it has reliable multi-region coverage; let thin-coverage SKUs ride the live toggle. Hidden hint: integratorMetadata carries our region-eligibility flags on each item — invisible to WM, but it's what the webhook reads to trim.
Recommendation
Matrix to configure · Cells to run · Ranking to tune

These aren't mutually exclusive — pick one config surface and one runtime engine. Configure with the Matrix (Option 2): it's the truthful many-to-many model, keeps shared regions like SB-02 and RC-02 in one place, and reads at a glance. Run on Fulfilment Cells (Option 5): availability then tracks who's actually on shift with the right kit, so a called-off driver's region drops out automatically instead of over-promising. Layer Ranked priority (Option 4) in as a Hyperdrive tie-breaker only where ops wants to steer ("prefer Corona for IE"). Address-first (Option 3) is the safety net underneath all of it — geometry always decides candidacy at the webhook, so we never route outside a real KML zone.

Whatever we pick, the runtime contract is fixed: the synchronous Draft webhook resolves address → candidate regions → Hyperdrive picks the region + driver best able to fill the cart, then mutates the WM cart's availability and pricing before replying. Mapping only ever defines the candidate set — inventory and the Hyperdrive score make the actual call. That's the principle these pages should be designed around: show the candidate set, but make the live decision legible.
