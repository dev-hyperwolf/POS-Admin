Concept A — the organizing idea

One console, six sections, and nothing wider than a number and a list.

Calm Ledger takes the owner's ruling literally. Six sections live behind one rail — Home/Insights, Customers, Audiences, Messages, Journeys, Loyalty — with Settings, integrations, audit and health under one gear, and Loyalty is physically a POS screen rather than a section borrowed into Engage. Home never grows past four numbers and one list — the four are active members, messages sent this week, redemption rate, and revenue Engage can claim credit for; the list is "needs attention," not a dashboard of fifty-one tiles fighting for the same eye. Every other screen is list + detail: pick a row on the left, read the record on the right, edit inline. There is exactly one dense surface in the whole concept — the Journeys canvas — because a journey genuinely needs to be seen whole; everything else earns its depth by scrolling, never by cramming.

The calm comes from a rule, not a mood: nothing in Calm Ledger shows a number without also showing the sentence that produced it. Audiences reads Customers who ordered 3+ times, last order over 45 days ago… before it reads 412 — the same discipline Klaviyo's plain-language segment builder and BLAZE's "on their 3rd visit" framing use (both flagged in the inspiration digest). Messages keeps that promise into send: the policy chain — consent coverage, quiet hours holds, frequency cap — sits above the Send button in the same sentence style, not behind a settings tab a marketer only finds after something goes wrong. Loyalty's earn rules and rewards use the identical sentence grammar — 2× points · Flower · Fri–Sun — because rule 7 says loyalty and promotions share one vocabulary, and a second grammar would be the first thing to make the console feel busy again.

What it costs: a console this literal about "one rail, one switcher" still has a seam. Loyalty's program screens live in the POS shell, not the Engage shell, exactly per rule 3 — so a marketer configuring a reward and a manager reading the register's member panel are looking at genuinely different chrome around the same ledger. This concept doesn't hide that seam; it shows both shells side by side in tab 7 so the trade is visible rather than assumed. And because every screen is list + detail, Calm Ledger is not the fastest concept for starting a one-off campaign from nothing — a goal-picker or canvas-first direction will feel quicker for that specific job. Calm Ledger is built instead for the console a marketer returns to every day, reads in ten seconds, and either acts on or closes.

What this concept trades away
  • Not the fastest way to start from nothing. A goal-picker or a canvas-first concept gets a one-off campaign live in fewer clicks. Calm Ledger optimizes for the tenth visit, not the first.
  • Two shells to keep aligned. Loyalty's POS screens and the Engage screens share tokens and a rule vocabulary, but they are not the same React tree — a change to the sentence editor has to land in both.
  • List + detail everywhere can feel like a lot of clicking for someone who wants a single glance at everything. That is deliberate — rule 5 says calm over dense, and Starbucks' own A/B test (inspiration digest §15) is the strongest evidence that a denser variant reads worse, not better.

Promo rules — the Trait & Condition Catalog

Define a condition once, in plain language. It shows up everywhere a rule gets built.

This is the answer to the owner's actual complaint: marketing can't say "if a customer falls into this segment, give them X" or "brand + category is 30% off, excluding this list" without a developer, and every new shape of that idea needs another ticket. The Trait & Condition Catalog is a settings screen — reached from the gear, same as the rest of admin config — where a condition is defined once: a name, a sentence template with fill-in blanks, the data it reads, a type, and the operators it allows. The moment it's saved it is available, unmodified, in the same sentence editor Audiences (tab 4) and Loyalty earn rules (tab 7) already use.

Three of the fourteen conditions below were added by Maria in Marketing, not by a developer — the catalog list says so, with the date, because "no developer needed" is a claim worth being able to check. What still needs engineering is the promotion engine underneath: it doesn't yet know how to evaluate an audience, a saved product list, or a store/channel scope. That gap is written out honestly at the bottom of this tab, not hidden behind a demo that pretends it already works.

Honest, not hidden — what production must add
  • The promotion engine's rule types — cart · product · user · bogo · time · payment — need three new attributes before any condition above can run for real: audience (resolves to a saved audience's live membership), product_list (resolves to a saved product list's members), and store/channel scope on every rule type, not only some of them.
  • The catalog itself is data, not code. Each row is a stored sentence template plus a field path and an operator set. Saving a new condition writes a row — it never touches the promotion engine's evaluator. The evaluator learns the three attributes above once, and every condition built on top of them — today's 14, or next year's 40 — works with no further deploy.
  • Live match counts (Catalog, New condition tabs) need a read-only query path into the customer/product tables that a marketer-saved condition can safely hit — rate-limited and cached, so Maria saving a condition can never trigger an unindexed scan against production.
Built from: the sentence editor and live-match mechanism are the exact .sentence/.tok pattern from engage/screen-audience-builder.jsx (tab 4) and the Loyalty earn-rules table (tab 7) — Concept A's rule that "loyalty and promotions share one vocabulary" (tab 1) extends one level deeper here, into the catalog that feeds all three. The catalog list and product-list editor reuse the Customers list's search + chip + table shell (tab 3) rather than inventing a new one.
Dev call-outs — what production must wire

Footnotes, not a floating panel — density budget applies to this tab too.

A fixed corner panel would be the one place in Calm Ledger that never goes away, which is exactly the kind of permanent chrome this concept avoids everywhere else. These six items are gathered here instead, each one grounded in a spot elsewhere in this document where it actually matters.

1
customer_id on the sale. Every POS sale line must carry the canonical customer_id at write time — not resolved later by matching a phone-number string against the identity graph. Today's join (tab 3, "Unified loyalty balance" pattern in engage/screen-customers.jsx) is exactly that string match, and it is the reason a pre-iter-104 bucket of points exists with no store tag at all.
2
Points ledger route. A single idempotent POST /loyalty/ledger/credit / /debit, keyed by sale_id, replaces any direct sheet or table write from the register (tab 7, tender step) or from a journey's loyalty-action node (tab 6). One route means one place a refund's point reversal can be audited.
3
Consent write. SMS/email grants and revokes (tab 3, "Consent" card) go through one consent-service endpoint regardless of where they originate — pos.checkout, web.landing, or console.manual — and the source + timestamp shown in every consent row must be the real write, not inferred from "customer exists so they must have consented."
4
Short-link redirect. hyp.wf/* (tab 5, SMS composer) resolves landing_page_id + a per-customer token server-side. The redirect must never leak which customer a link belongs to in the URL itself, and must 404 cleanly rather than fall through to a generic page on an expired token.
5
Landing page render. The 21+/state gate toggle (tab 5, block builder) is a per-page setting stored with the page, not a global flag — the storefront itself stays gate-free per rule D-024a, and a page built without the gate must be a deliberate choice visible in the builder, not a default anyone can miss.
6
Promotion-engine rule compatibility. Loyalty earn rules and rewards (tab 7) must compile to the exact same IF/THEN vocabulary as the production Promotions Suite — cart · product · user · bogo · time · payment, plus store and channel scope — so the one sentence editor shown throughout this concept is not a second rule language pretending to be the first.
