Concept D — the organizing idea

The journeys canvas is the primary surface. Everything else is either a view over it or a builder that feeds it.

A one-off campaign is a one-node journey (trigger: manual send → message → exit), so Messages never became a second automation system to learn — it's the same canvas at its smallest. The block builder that composes an email or a landing page opens inside a message node rather than in its own top-level screen. Loyalty actions (give points, change tier) are nodes with the same shape as a message node, not a bridge to a separate system. Audiences aren't a destination you pick before sending — they're the entry condition written into a trigger or branch node. The result is the fewest top-level screens of the four concepts: Home, Customers, Audiences, Messages, Journeys, Loyalty, and one settings gear — and four of those seven are, structurally, just filtered views of the canvas or a library that feeds it.

What it costs: a marketer who wants "just send a text to my VIPs" has to internalize, at least once, that they are creating a journey with one node — a small conceptual tax that Concept A (calm ledger) and Concept B (goal picker) don't ask for. This Home tab is deliberately thin — four numbers and one list — because the canvas itself is the dashboard once you're in it.

Journeys — the primary surface

One canvas, a six-kind palette, and a complete win-back journey laid out end to end below.

The palette below is deliberately capped at six node kinds — trigger, wait, branch, message, loyalty action, exit — the same vocabulary engage/screen-flows.jsx already uses (NODE_ICON/NODE_HUE). Braze's "Full Step" composite (delay + filter + message in one card) was considered and rejected here: it would let a node's meaning depend on how a builder folded it, and this concept's whole bet is that a canvas stays calm by keeping every node's meaning fixed by its kind, not by its configuration. The branch node below is selected — its property panel is open on the right, exactly what opening a real node would show.

Promo rules — conditions are nodes, data sources are connector cards

Marketing's problem: "if a customer falls into this segment, they get X" or "brand + category is 30% off, excluding this list" currently needs a developer. This tab is where that stops being true.

A promotion is a small graph, on the same canvas style as Journeys (tab 5): source nodes (Audience, Product filter, Cart, Store, Time, Customer field) feed combine nodes (AND, OR, NOT/Exclude) which feed a single action node (percent off, reward, points multiplier, free product) carrying its own store/channel scope. Every node shows a live match count, so the graph is checkable before it goes live, not after. New data — a table, a feed, a one-off list — comes in through a connector card in the Data sources drawer below: pick a source, and its fields become source nodes immediately. No developer touches this path.

Two worked graphs below: a product-and-category discount with an exclusion list, and a one-hop audience reward. Both produce the same plain-language readout a reviewer can sign off on without reading the graph.

Dev call-outs

What production has to wire for this concept to be real, not a claim of what already exists.

Six items, each named in the tabs above where it matters. This is the "small fixed panel" from the brief, made its own tab because the canvas-first layout left no chrome to pin it to without covering a node.

customer_id on the sale
Every register sale needs a resolved customer_id before tender completes, or the earn/redeem tender line (Loyalty tab) has nothing to post against. Today this depends on phone-number lookup at the register; a missed match silently earns nobody points.
Points ledger route
One ledger, written by two callers: the register's tender step and a journey's loyalty-action node (Journeys tab, +150 bonus points). Both need the same idempotent write path keyed on (customer_id, reason_code, source_event_id) so a retried journey step or a re-tendered sale can't double-credit.
Consent write
SMS/email opt-in and opt-out both need a single write path, called from the register (kiosk sign-up), the web checkout, and inbound STOP replies. The branch node in Journeys reads this table live — a write that lands in a different table than the branch reads from will silently misroute customers.
Short-link redirect
hyp.wf/x7Kq2p (Messages tab) needs a redirect service that resolves a short code to a specific landing-page render, per-recipient, so click tracking and the gate toggle both know which version of the page a given customer opened.
Landing page render
The block-builder output (Messages tab) has to render server-side as an actual public page with the per-page 21+/state gate evaluated before content shows — the gate is a page setting in this concept, not a global switch, and storefront stays gate-free per rule D-024a.
Promotion-engine rule compatibility
Loyalty earn rules and reward redemptions (Loyalty tab) are written as IF/THEN sentences in the same vocabulary as the Promotions Suite (cart · product · user · bogo · time · payment, plus store/channel scope) — one rule engine underneath, so a reward is legible as "a promotion whose action is points."
