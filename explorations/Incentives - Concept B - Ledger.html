Concept B · Ledger

Every number is auditable. Standings, bounties, earnings and ingestion are four views over one ledger, and every figure on screen can show its own arithmetic.

The organizing idea is that a leaderboard is a claim, and a claim a budtender is paid on has to be checkable by the person who is paying. So this concept never shows a rank without also being able to show the window it was measured over, the sources that fed it, the sales it counted, the refunds it netted out, and the money it could not attribute to anybody. Selecting any row opens a computation trail on the right: gross, refunds, net, and the residual — the same shape a bank statement uses, because that is the shape people already know how to argue with.

It serves best the operator who has been burned by a dashboard — a floor manager or an owner who has had a number contradicted at the counter and now wants the receipt before they hand out $150. It also serves the person doing the boring work: ingestion is a first-class screen here, not a settings page, because in this estate the thing most likely to be wrong is not the ranking maths, it is that Blaze never carried an employee on the sale (assignedEmployee measured at 0 % populated) and nobody noticed for a week.

What it trades away is celebration. There is no confetti, no streak, no trophy shelf, and the budtender-facing surfaces are deliberately quieter than a SparkPlug-style app would make them — a projected payout is labelled as projected and sits next to what has actually settled. That is a real cost: this concept will motivate less on its own and rely more on the bounty itself doing the motivating. It also spends screen width on proof, so it wants ≥1280px and degrades to a single column below 1180px.

The shape is borrowed, not invented. The two-column layout — a DataTable-first left column with sort, filter and pagination, and a detail panel on the right — is pos/screen-catalog.jsx’s exact shape, down to PAGE_SIZE = 25 and its pageWindow() ellipsis pager. The computation trail is the audit trail from the AOV manager card in pos/screen-aov.jsx, promoted from a footnote to the point of the screen. The source-freshness line is screen-catalog.jsx’s own freshness convention (product data live · confirmed 2m ago), applied per store × source. The shell is the Engage skeleton: HWRail, a 212px module sidebar, a 56px topbar with the theme toggle.

Everything below is drawn with existing atoms. Where a composite is needed it is built visibly out of them and captioned as such — the trail panel is a Card padding=0 with a card head and hairline-separated rows; the standings table is DataTable with a residual row; the freshness stack is three text lines with a status dot. No new colour, no new type size, no new control height.

What “auditable” costs, honestly
  • Every screen is denser than its counterpart in a celebration-first concept. A budtender glancing between customers sees more words.
  • The detail panel eats 392px. Below 1180px it drops under the table, so the trail is a scroll away on a laptop.
  • Disclosures are collapsed by default. If a reviewer never opens one, this concept reads as a plainer version of the others — the proof only pays off when it is opened.
Screen · #/ · incentives/screen-standings.jsx

The board is a table you can sort, filter and page — and the panel beside it shows how the selected row’s number was reached.

Left column is DataTable in screen-catalog.jsx’s shape: a surface2 head with sortable columns, hairline-separated rows, a selection bar on the chosen row, and the same “Showing 1–8 of 10” pager underneath. Screen · #/data · incentives/screen-data.jsx

The strongest screen in this concept. A run report reads like a bank statement, a conflict is a diff, and an unresolved identity shows its evidence before it asks you to bind it.

Ingestion is where this module will actually be wrong, so it gets the most room. Connections are one row per store × source with freshness and the last error verbatim. Every upload produces a run whose counts must satisfy rows_read == inserted + unchanged + conflicts + rejected — the invariant is printed, not implied. Rejects name the row number and the reason. Conflicts show stored against incoming, field by field, and default to keeping what is stored.

Screen · #/contests/new · incentives/screen-contest-builder.jsx

A plain vertical form — no wizard, no steps — with a preview that says what this bounty would have counted over the last seven days.

Screen · #/earnings · incentives/screen-earnings.jsx

Projected and settled are two columns that reconcile at the bottom. Nothing here moves money.

A projection is what you would earn if every open bounty settled on today’s standings; it changes with every sale, including someone else’s. A settlement is a written row in inc_points, once per person per round, and it does not change. Showing them as one number is how a budtender ends up believing they are owed something they are not, so they are never added together — the only line that combines them says so explicitly.

How a projection is computed

Each open bounty is evaluated on the current ledger as though its window had just closed, then the reward structure is applied to that standing. Ties split. The result is cached against ledger_version, so it only recomputes when the ledger actually changes.

It is never written to inc_points. Only settlement writes.

Screen · #/goals · incentives/screen-goals.jsx

The AOV goal, absorbed as one bounty kind and left recognisable: store default, per-person overrides, and the audit trail that made this pattern worth keeping.

This is the one screen that already exists in production shape (pos/screen-aov.jsx’s manager card) and it is deliberately barely redrawn — the same store-default-plus-override rule, the same required reason, the same “a clear is itself a decision worth an audit line”. What is new is the disclosure: an AOV figure is a division, and this concept shows the numerator, the denominator and the window rather than a number with a meter under it. The /api/aov/* contract is unchanged; it is served from the new ledger.
