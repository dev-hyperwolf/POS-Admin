Concept B — the organizing idea

Home doesn't ask "what do you want to build" — it asks "what are you trying to make happen."

A marketer opening Engage on a Tuesday morning is not thinking in nouns (audience, campaign, journey) — they're thinking in outcomes: get the people who stopped coming back to come back. So Home is five goals, not a dashboard of fifty-one tiles. Pick one and Engage pre-builds the three objects that outcome needs — a plain-language audience, a message with a real SMS body and a landing page, and a journey with the right trigger and exit — and shows all three end to end before anything sends. The six sections (Customers, Audiences, Messages, Journeys, Loyalty, plus settings under one gear) still exist in full underneath; the goal picker is a front door into them with the tedious first draft already done, not a replacement for editing directly.

The number-51-tiles problem is solved by subtraction, not organization: one row of four numbers that answer "is anything on fire," one list of what needs a human today, and then the goals. Insights-as-dashboard never gets a tab of its own in this concept — insights live next to the object that produced them (a flow's own conversion count, a campaign's own delivery rate), per the synthesis note that analytics belongs beside the action, not in a separate reporting screen.

Journeys — one canvas, small palette

Six node types. The win-back journey shown end to end, with counts at every node.

trigger · wait · branch · message · loyalty action · exit — nothing else. A one-off campaign is still a "Messages" object, not a one-node journey (that's Concept D's move, not this one); Journeys is reserved for anything with more than one step or a wait. Loyalty actions (grant points, unlock reward) are native nodes here, not a bridge to a separate system, per the synthesis note on the strongest consoles surveyed.

Promo rules — recipes, not code

Marketing builds the promotion. Engineering builds the four attributes it's assembled from, once.

The owner's problem: "if a customer falls into this segment they receive X" or "brand + category is 30% off excluding this list of products" cannot be built by the marketing team today — every new shape of promotion needs a developer to add the concept, so a Tuesday idea sits in a ticket queue. Concept B's answer is a recipe library: promotions start from a sentence with slots a marketer fills in — audience, brand, category, product list, store, channel, percent, reward — not a blank rule builder. Eight recipes cover most of what marketing actually asks for; the demo data below is labelled demo.

When no recipe fits, "Teach a new phrase" is a three-step wizard: write the sentence in plain English with {slots} marked, map each slot to a data source (the wizard suggests the mapping, a marketer confirms or repoints it), then test it against live counts before it saves as a new recipe anyone on the team can reuse. Two of the eight recipes below were taught this way — no developer involved either time.

Before this can be real — the honest dev call-out
Every recipe and taught phrase on this tab is data, not code — a template row plus a slot-to-source mapping, stored the same way a saved audience sentence is stored today. What production has to add to the promotion engine, once, is the attribute set every recipe reaches for: audience, product_list, store, and channel as first-class promotion attributes alongside the existing cart · product · user · bogo · time · payment types (see the Loyalty tab's earn-rule note — same engine, same gap). Once those four exist, "teach a new phrase" never touches the engine again — every new recipe after that is only ever a new row, not a new deploy.
Dev call-outs

What production has to wire for this concept to be real, not a mockup.

Every screen above is demo data laid over real component shapes. Nothing here fires, ledgers, or sends. This tab is the honest list of backend work the mockup is standing in for — six items, each named to the exact surface it touches.

customer_id on the sale
Every POS sale must carry a resolved customer_id before tender completes, or the register-side member panel (Loyalty tab) and the earn line have nothing to attribute to. Today's guest-checkout path can complete without one — that path needs an explicit "skip loyalty" state rather than silently omitting the field.
The points ledger route
One write path for every points event — earn, redeem, expire, manual adjustment, referral bonus — each a signed ledger row, never a balance column overwritten in place. The register's tender step, the Journeys "loyalty action" node, and manual staff adjustments in Customers all call this same route so the balance can never drift between surfaces.
Consent write
SMS/email/push consent needs one write path that always records source + timestamp (checkout, wallet-pass install, landing-page form) — the Customers tab's consent block and the Messages policy-chain check both read from this, and a consent row with no source or timestamp is what produced the 14 held customers on Home today.
Short-link redirect
hyp.wf/x7Kq2p needs a redirect service that resolves per-recipient (so click tracking and per-customer merge tags work) and expires or rotates per campaign — this is what keeps the SMS body itself free of any cannabis content, per D-024a.
Landing page render
The block-builder canvas (Messages tab) needs a render path that respects the per-page 21+/state gate toggle, pulls merge tags live (points balance, first name) at request time rather than at send time, and never renders cannabis content on a gate-off page.
Promotion-engine rule compatibility
The Loyalty earn-rule sentence editor (Loyalty tab) needs to compile to the exact same rule types as the production Promotions Suite — cart · product · user · bogo · time · payment, plus store/channel scope — so a reward really is "a promotion whose action is points," not a parallel rule language that drifts from the one the register already evaluates at checkout.
Also flagged, not itemized above
  • Alpine IQ import-then-retire is a one-time migration, not a standing integration — no screen in this concept reads from Alpine at runtime.
  • Quiet-hours and frequency-cap enforcement (shown honestly in the Messages and Home policy-chain panels) must live in the send path itself, not just the compose-time estimate — an estimate that isn't re-checked at actual send time is how a "held" count quietly becomes a real violation.
  • The register member panel and the Customers CRM record are described here as "the same component" — that only stays true if POS and Engage share one frontend package for it, not two copies that drift.
