Concept C — the organizing idea

The member record is the centre of gravity. Every other section is a view over customers, not a separate database.

Six sections stay in the tab list because the brief requires them, but only one of them is actually a place things live: Customers. An audience is a saved filter over customer rows. A message is a thing sent to the customers an audience returned. A journey is a sequence of things that happen to customers who match a trigger. Loyalty is a set of rules that change a field on the customer record — points, tier, a reward's eligibility. Nothing in Audiences, Messages, Journeys or Loyalty owns a customer; they all read and write the same record. The clearest proof of that is literal, not rhetorical: tab 2's CRM record and the POS register's member-lookup panel are rendered from one JavaScript template in this file, called twice — open the page source and there is exactly one function, not two look-alike copies that could drift.

That centre-of-gravity idea is also how this concept avoids the 51-tiles problem the owner rejected. Home shows exactly four numbers — reachable audience, points liability, this week's sends, active journeys — and exactly one list: a single unified "needs you" queue that merges what would otherwise be four separate review screens (a pending send, a stalled journey, a stale audience, a redemption dispute). There is no dashboard beneath the fold. Insights lives in this same tab rather than as an eighth section, because the only insight a calm console owes a marketer on login is "are my numbers current and does anything need me" — anything deeper is a click into the customer record that produced it.

Why four numbers, not fifty-one tiles
Starbucks tested a denser, more analytical rewards view and reverted after it produced more errors in real tasks — the owner cited the same finding. Every number that isn't one of the four here is one click away, inside the customer record or the audience that produced it, never bolted onto Home as a fifth tile.

Audiences — a saved filter over the customer table

An audience is not a list you build and copy — it's a sentence that re-reads the customer table every time it's used.

The sentence editor and the AI prompt both compile to the same thing: a filter over customer record fields. There is no separate "segment" object with its own storage — a saved audience is a name, the sentence, and a refresh cadence. The live size updates as soon as a clause changes, and the sample of 5 links straight into the record component from tab 2, because a marketer checking "who is this" should land on the same record a budtender sees, not a stripped preview row.

Messages — compose, the block builder, and the policy chain

One block builder serves email and landing pages, because an SMS never carries content — it only carries a link into a page this builder made.

Compose walks Audience → Channel → Content → Schedule → Policy check → Send, top to bottom on one screen rather than a wizard, so the policy numbers are visible while still editing. The block builder is the same canvas whether you're building an email body or a landing page ("squeeze page") — the only per-context control is the 21+/state gate toggle, which only does anything on a landing page. The SMS composer never gets a rich editor: it shows the fixed-format short body next to a live preview of the page it opens, because that is the entire SMS surface by rule D-024a.

Journeys — customer rows moving through a small canvas

Six node types. A journey is what happens to a customer record when it starts matching a trigger, and every node's number is a count of customer rows, not an abstract "conversion."

Trigger · wait · branch · message · loyalty action · exit — that's the whole palette. Loyalty actions (give points, adjust tier) sit as native nodes rather than a webhook out to a different system, matching the pattern Alpine IQ and Braze both use. Below is a win-back journey shown end to end with enrolled/converted counts at every node, because a canvas that only shows the shape of the flow without the numbers moving through it doesn't answer the question a marketer actually has: is this working.

Promo rules — every field is already a condition

The marketing team's problem was never the rule logic. It's that today, "if a customer falls into this segment they receive X" requires a developer to write it. Concept C fixes that without a separate rule builder screen — because the customer record, the product record, and the order record are already the centre of this concept, any field on any record can be turned into a condition in place.

Hover a field on a member record — "Favorite store: Corona" — and it offers Use as condition: favorite store is Corona. Hover a field on a product record — "Brand: Raw Garden" — and it offers the same thing. There is no separate vocabulary to learn: whatever the record already shows is whatever the rule can filter on. Picked conditions land in the rule tray pinned to the bottom of the screen, where they're joined by AND/OR, counted live, and paired with a "Then…" action and a store/channel scope — never leaving the record you were just looking at.

Two conditions need a saved set, not a single record: "everyone in this segment" and "every product except this list." Those are saved lists — a customer list (an audience) or a product list (an exclusion list) — built once, then referenced from any rule's "in audience…" or "excluding…" clause. The honest limit is at the bottom of this tab and repeated on tab 8: none of this works until the production promotion engine treats audience, product list, store, and channel as rule attributes the same way it already treats brand and category.

What production has to expose
Every "Use as condition" action above only works if the field it's attached to is already a rule attribute the promotion engine understands. Concretely: audience, product_list, store, and channel all need to become first-class attributes on the production promotion engine, the same way brand, category, and price already are — "in audience Lapsed VIPs" and "excluding list Clearance exclusions" aren't new rule types, they're the existing cart/product/user rule types reading one more attribute each. Lists themselves are data, not code: a product list and a customer list are just a saved set of IDs the engine joins against, so adding a new list never touches the rule language.
Built from: the same kv row used for every Identity/Consent field elsewhere in this file, with one modifier class (condrow) adding a hover-revealed action — the affordance is a CSS state on an existing primitive, not a new field component. The tray reuses chip, segctl and field exactly as the Audiences (tab 3) and Loyalty (tab 6) rule surfaces already do, pinned with the same sticky pattern as .doc-head at the top of the page.
Dev call-outs — what production must wire, named once

Every number in this mockup is demo data. This tab is the honest list of what has to be real before any of the previous six tabs can be.

Concept C's "one customer record" idea only holds if every surface actually reads and writes the same backend row. These six items are the seams where that could quietly stop being true — each is called out again inline on the tab where it bites hardest, and repeated here as the single list a backend engineer can work from without reading the rest of the file.

customer_id on the sale
Every POS sale row must carry a resolved customer_id before earn rules, tier multipliers, or reward redemption can post to the ledger. Today a sale can complete with no customer attached (guest checkout) — that path needs an explicit "skip loyalty" state rather than a null that silently breaks the tender-step math shown in tab 6.
The points ledger route
One ledger, append-only, per owner rule 1 — every earn, redeem, expiry, and manual adjustment is a row, not a mutated balance column. The $42,180 liability figure on Home (tab 1) is a SUM over this ledger, not a cached total, so it can't drift from what tab 6's tender step actually posts.
Consent write
SMS and email consent each need a source and a timestamp written atomically with the grant — console.manual, landing.optin, register.checkin, etc. — because tab 2's Consent card and the compose-time policy check in tab 4 both read this same write, and a consent flag with no source is not auditable if a customer disputes a message.
Short-link redirect
hyp.wf/* needs a redirect service that resolves per-recipient (so click tracking can tie back to one customer row) and renders the correct landing page version including its own gate-toggle state, shown in tab 4's SMS composer. A broken short link is the only thing an SMS-only message can fail on, so this is the single highest-leverage integration point in the whole system.
Landing page render
The block builder in tab 4 needs a real renderer that respects the per-page 21+/state gate toggle and serves merge tags server-side (a customer's real first name, points balance, tier) — the storefront itself stays gate-free per rule D-024a; only pages built here can carry a gate.
Promotion-engine rule compatibility
Tab 6's earn rules and tab 3's audience sentences both need to compile to the production promotion engine's existing rule types — cart · product · user · bogo · time · payment, plus store and channel scope — per owner rule 7. A reward is a promotion whose action is points or a discount; if the loyalty rule builder speaks a different rule language than the Promotions Suite, this concept's "one sentence editor" claim breaks the first time someone builds a rule the engine can't run.
