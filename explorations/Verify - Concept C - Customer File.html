Verify — Concept C: Customer File

DESIGN EXPLORATION · Exploration — sample data · Hyperwolf Verify — Didit parity, Hyperwolf engine
Concept C · organizing idea

The person is the record, not the session. Verify is a compliance file cabinet: you search a customer, you open their file, and every check anyone has ever run on them is on one page in date order.

Didit's console — and the other three concepts — put the session first: a long table of verifications, one row per attempt, and a person is whatever you can infer by reading several rows. That is the right shape for a vendor who sells checks. It is the wrong shape for a dispensary, because the questions a dispensary actually gets asked are all about a person: is this the same human who signed up in 2025? When does their licence expire and have we asked them to re-verify? Is this a second file for someone we already know? Who approved them, and on what evidence? Each of those takes three or four clicks in a session-first console. Here they are one page.

So the file is the primary object. It opens with the person, their current standing and their expiry countdown; the middle column is a vertical timeline of every verification they have ever been through — the website sign-up in 2025, the session imported from Didit, an in-store re-verification, a Kyc Expired sweep, the resubmission after it — each one a card you can open into full session detail. The right column is the evidence that belongs to the person rather than to any one session: documents on file with expiry countdowns, face templates, 1:N matches to other files ("possible duplicate of …"), list membership, and the analyst trail across every session at once.

Review is a triage board, not a queue. Sessions in In Review are cards on a board with a column per reason — Liveness · Face match · Document · Duplicate person · IP/device · Age. An analyst picks a column, works it, and drags a card onto a colleague to assign. Reason-first columns matter because the reasons need different people: a duplicate-person card is a records judgement, a liveness card is a media judgement, and a document card is usually a re-shoot. A single ranked queue mixes all three and every analyst context-switches on every card.

The workflow builder is a pipeline diagram, left to right: Document → Cross-check → Liveness → Face match → Age → IP → Lists → Decision. Each stage is a card carrying its thresholds and, crucially, what happens on fail — retry, review, or decline. The failure route is the part of a verification policy people get wrong, and a form full of number inputs hides it. Stages the Hyperwolf engine cannot run (NFC, AML, database validation, proof of address) sit in the diagram greyed out and labelled "Not available on the Hyperwolf engine", so an imported Didit workflow round-trips without anyone quietly believing we run a check we do not.

Who it serves best. Compliance, records and anyone who has to answer a question about a human being — an audit, a state inspection, a "did we let this person in twice" question, a re-verification campaign. It is also the only one of the four concepts where the re-verification cadence is legible: expiring documents and Kyc Expired people are a home-page shelf, not a filter you have to remember to apply.

What it trades away. Density for single-session work. An analyst clearing thirty routine liveness cards is slower here than in a table-first concept: the file frame is heavier, and opening a person to read one session is a detour. Concept C answers that with the triage board (tab 5) and a secondary verifications table (tab 6) that keeps the flat Didit-shaped list for people who want it — but the table is deliberately the second-class citizen, and if the module's real daily load turns out to be volume triage rather than records work, that is the argument against this concept.

Composites built visibly out of atoms, named where they appear: the file frame is a three-column Card padding=0; the timeline is a stack of Card + Pill with a 2px rail drawn in CSS; expiry countdowns are BarMeter; duplicate rows are Avatar + Pill + BarMeter; the triage board is the fulfilment kanban from pos/screen-orders.jsx with reasons as stages; the pipeline builder is a row of Cards with Pill thresholds; every panel head is SectionHead. Session detail opens as Sheet from the file, or full-page from the table. No new primitive is invented.

At ~150 sessions a month the console is not a volume tool. That is the whole case for a file-first design: there is time to look at a person properly, and almost never a queue to grind. Every other number on the following tabs is illustrative and marked as such.
The four questions Concept C is built to answer in one page
1 · Same human?
The file's timeline shows every check on one person, oldest first, with the document and face evidence beside it. "Is the person in store today the person who signed up in 2025" is a visual comparison, not a query.
2 · When do we ask again?
Documents carry an expiry countdown on the file and on Home. A person whose licence expires inside 60 days is on the Home shelf before anyone gets turned away at a register.
3 · Do we already know them?
1:N face search runs against every stored template. A possible duplicate is a row on the file with a score, a link to the other file, and one Merge action that is audited and reversible in the trail.
4 · Who decided, on what?
The analyst trail spans sessions, so the file answers "who approved this person and what did they see" without opening five sessions in five tabs.
Honesty rules that show up on every screen here: liveness scores always carry open model · uncertified; imported sessions are labelled Verified by Didit, imported and never count toward Hyperwolf engine accuracy; usage says no per-check fee (own engine) rather than inventing a cost; a panel with no data renders an empty state naming the window, never a zero chart.

What Home deliberately does not have
No leaderboard, no approval-rate gauge, no conversion funnel above the fold. At this volume those numbers move on noise, and a gauge that swings 8 points because two people abandoned is worse than no gauge. Conversion and drop-off live on the Verifications tab where the filter that produced them is visible.

What the file makes cheap
  • "Same human?" — the 2025 document portrait and the 2026 selfie sit two inches apart.
  • "When do we ask again?" — one countdown, on the document that governs it.
  • "Do we know them already?" — the duplicate panel is on the file, not a separate report.
  • "Who decided?" — one trail across five sessions instead of five trails.
What the file makes expensive
  • Reading one routine session takes a person load first — mitigated by search jumping straight to the card, and by the flat table on tab 6.
  • A person with 40 sessions needs the timeline collapsed by year; the design shows 5.
  • Three columns need ~1120px. Below that the columns stack, and the timeline is the one that stays.

Approve writes the review row, the event and the audit row in one transaction and fires the outbound webhook. Ask to resubmit asks which nodes (nodes_to_resubmit) and mints a fresh capture link. Edit data corrects extracted fields and stores the field-level diff on the review. Merge is the duplicate action from the file, reachable here because that is where you notice it. Delete opens a deletion request — never an immediate delete. Overriding a Declined session needs admin; everything else needs analyst.
Imported sessions look different here
An imported session shows Verified by Didit, imported, the node table renders Didit's arrays as they were received, the score column carries no Hyperwolf threshold, and the session is excluded from engine accuracy panels. Nothing is recomputed — recomputing a 2025 decision with a 2026 model would be a new decision wearing an old date.
Four-eyes, off by default
A workflow flag can require a second approver on any session an analyst approves out of In Review. It is off by default because at ~150 sessions a month the second pair of eyes is usually the same person an hour later, which is theatre. Turning it on adds a second signature row to this trail.
Screen 4 · Review — triage board

Review is a board with one column per reason, because the reasons need different people. Cards are sessions; you drag a card onto an analyst to assign it.

A single ranked queue makes every analyst context-switch on every card: a duplicate-person card is a records judgement, a liveness card is a media judgement, a document card is usually just a re-shoot request. Sorting by reason lets one person work one kind of decision all the way down, which is both faster and more consistent. Every card carries the reason codes it was enqueued with. Working a card writes idv_reviews, idv_session_events and idv_audit in one transaction — the card disappearing from the board is the last thing that happens, not the first.
Columns are reasons, not stages
Nothing moves left to right. A card leaves the board by being approved, declined or sent back for resubmission — dragging is only for assignment. A session with two reasons appears in the column of its highest-priority reason and shows the other as a second chip, so no card is ever in two columns.
The honest caveat on this whole tab
Today there is nothing to triage: 0 waiting at Didit, 0 sessions in the last 30 days. This board is designed for the day the Hyperwolf engine's thresholds are new and unfamiliar and everything lands in review at once — which is exactly the first week after cutover.
Screen 5 · Verifications — the secondary surface

The flat, Didit-shaped list is kept, deliberately as the second-class citizen: it is for exports, spot lookups and anyone who already knows the session number.

Same columns Didit shows — session, user, status, workflow, channel, vendor_data, date — plus the reason codes, because a status literal without its reason is not actionable. Every row opens the customer file with that session's card selected, which is the one place the concept insists on: even the table routes you back to the person.

Screen 6 · Workflows — pipeline builder

A workflow is drawn as the pipeline it is: Document → Cross-check → Liveness → Face match → Age → IP → Lists → Decision. Each stage carries its threshold and, on the card, what happens when it fails.

Failure routing is the part of a verification policy people get wrong, and a form of number inputs hides it completely. Here every stage says retry, review or decline in words, and the reason code it emits. Stages the Hyperwolf engine cannot run are drawn in the pipeline, greyed, labelled "Not available on the Hyperwolf engine" — they are stored so an imported Didit workflow round-trips, and they are never silently treated as passing.

Screen 8 · Lists

Eleven list types, four real entries between them. The feature is not small; the data is — and the screen says so instead of looking busy.

Every entry stores a hash and a masked display value, never the raw document number, email or phone. A face entry points at a stored template rather than an image. Adding a person to a blocklist is a judgement about a person, so it is always an explicit, audited action with a reason — nothing is auto-added except device and IP signals flagged INJECTION_DETECTED, and those land on a custom "suspect devices" list for review, not on a blocklist.

Screen 10 · States

Loading, empty, error and degraded — drawn for real, because a console about identity that fails vaguely is worse than one that fails loudly.

Skeletons keep the header the loaded state will have, so nothing moves when data arrives. Empty states name the window in words instead of drawing a zero chart. The not-connected state is a named title and plain body with a retry. And "backend up, engine down" is a distinct state with its own badge and its own customer-facing copy.

Deletion is two steps
1 · Request — an analyst records the target (person or session), the instruction (operational_session_delete or privacy_erasure), and whether a face template is retained for blocklist purposes.
2 · Execute — an admin runs it. Media files, document rows, decision PII and templates go; a tombstone session row stays with deleted_at so counts and audit stay truthful.
Deleting Didit's copy after import is a separate, irreversible step at Didit that this console never performs on the owner's behalf.
Concept C in one line
Organise the console around the person and the compliance story tells itself; organise it around the session and somebody has to reassemble that story by hand, every time, under pressure, in front of an inspector. The cost is density on routine single-session work, and tabs 5 and 6 are the concession to it.
