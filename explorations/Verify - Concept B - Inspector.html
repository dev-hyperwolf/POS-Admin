Concept B · organizing idea

Evidence first, decisions second. The console is not a set of tables with a detail page behind them — it is an inspector, and the review queue is the home screen.

The person this concept is built for is the fraud analyst, not the reporting manager. That person's whole job is: look at the document, look at the face, look at the frames where the face responded to the challenge, decide. Every pixel that is not evidence is competing with the job. So Concept B opens a session as a full-bleed inspector: the document front and back, the portrait crop and the selfie, and the challenge frames fill the canvas at a size you can actually judge, with zoom and side-by-side compare. The scores sit in a thin overlay rail on the right — visible, never in the way — and the actions live in a keyboard bar along the bottom, because an analyst who has to move a mouse between every decision reviews a third as many sessions.

The dashboard is a strip, not a page. Six numbers across the top of the queue: to review, oldest wait, approved and declined today, sessions this month, engine health. That is the whole dashboard. A separate dashboard page would be a screen an analyst opens once and never again, and it would push the queue — the actual work — one click away from the front door.

Tables still exist and are still good. The verifications table is tab 4, filterable by status, workflow, reason code and channel, and it is where you go when you are answering a question rather than clearing a queue. It is deliberately secondary. Concept B's bet is that the daily surface is the queue and the inspector, and everything else is a place you visit.

What it wins. Speed, and catching fraud. Portrait-versus-selfie side by side at a real size catches a printed-photo attack that a 42px thumbnail never will. A barcode-versus-OCR field diff shown line by line catches an altered front that reads fine on its own. A challenge timeline that shows the flash sequence next to the frames where the face responded is the only honest way to look at a liveness result from an uncertified open model — you are showing the analyst the evidence rather than asking them to trust a number. What it costs. Didit-familiarity. Anyone who has lived in the Didit console will look for a dashboard page and a verifications list as the front door and find a queue instead. The mapping is learnable in a minute, but it is not free, and if the primary user turns out to be a manager checking on volume rather than an analyst clearing work, Concept B is the wrong shape.

Composites built visibly out of atoms, named where they appear: the strip is six Cards sharing one border; a queue row is Avatar + Pills + mono columns inside a DataTable-shaped grid; the signals rail is a stack of BarMeter with a threshold tick; the action bar is PBtn in variant=accent/primary/danger on the rail surface; the cross-check diff is HDTable; similar faces is a grid of Card padding=0; the capture frames are Card radius=r20. No new primitive is invented anywhere in this concept.
The five things the inspector puts on one canvas
Document, front and backFull width, zoom 1×/2×/4×, glare and blur called out where the engine saw them
Portrait crop vs selfieSide by side, same height, match score between them
Barcode vs OCR fieldsDiffed line by line; a mismatch is a red row, not a warning icon

Similar faces (1:N)Cosine search across stored templates; a near-duplicate person is a fraud signal, not a merge suggestion
Everything else — scores, IP, device, list hits — is the overlay rail. It never takes canvas width away from the evidence.
Keyboard map — the whole action set
J / KNext / previous session in the queue

DDecline — asks for a reason code before it writes

What Concept B is honest about
Liveness is the weak point and the screen says so
No open-weight presentation-attack model is ISO 30107-3 certified. Every liveness score in this concept carries open model · uncertified next to it, in the rail, in the preview and in the exports. The design compensates the only way it honestly can: a server-issued nonce the client cannot predict, a flash sequence, the frames shown to a human, and a queue that a human actually clears.
Three more labels that are not decoration
  • Verified by Didit, imported — on every migrated session; those never count toward Hyperwolf-engine accuracy panels.
  • Not available on the Hyperwolf engine — greyed in the workflow builder for NFC, AML, database validation and proof of address. Stored so an imported workflow round-trips, never pretended.
  • no per-check fee (own engine) — the Usage cost column. Hosting is not metered, so it is not shown as a per-check number.

Priority is set by the workflow, not by the analyst: a blocklist-adjacent or duplicate-person reason is P1, a threshold reason is P2, an advisory reason is P3. Wait time is measured from the moment the engine wrote In Review, not from session creation — a session that sat in Awaiting User for ten minutes was waiting on the customer, not on us.
What the strip is, and what it deliberately is not

Six numbers, one row, above the work. It answers "is anything on fire and is the engine up" in a glance and then gets out of the way. It is not a dashboard page: there is no chart, no date-range picker, no per-store breakdown, no funnel. Those questions are real but they are not this screen's questions — they live on the Verifications table with filters, and on Usage.

The rule the strip follows when there is nothing
A panel with n:0 renders the count as a dimmed zero with the window written in words — "0 in the last 30 days" — never a flat chart, never a dash. On the day this was drawn the live console's answer to four of these six really is zero.
Queue rules an analyst can rely on
AssignmentClaiming is optimistic and reversible; two analysts opening the same row see each other's name in the bar
OrderingPriority, then wait. Never re-sorted under you while you are on a row
After a decisionThe row leaves, the selection moves to the next row, focus stays on the canvas
UndoNone. A decision writes an audit row; a wrong one is corrected by a second, also audited, action
RefreshPolls on a version field; an unchanged version does not re-render the list under your cursor
The last one is the same ledger_version short-circuit Bounty uses — here it matters more, because re-rendering a queue while someone is pressing A is how you approve the wrong session.

What each action actually writes
A Approvestatus → Approved · person created or updated · face template stored · kyc_expires_at set · webhook fanned out
D Declinestatus → Declined · reason code required · terminal unless an admin overrides
R Resubmitstatus → Resubmitted · you pick the nodes · customer gets the same link back at that step
N Notetrail row only · no status change · visible in the export
L Listentry on a chosen list · document and face entries store a hash or a template, never the raw value
M Mergesets merged_into on one person · rewrites nothing · both histories stay readable
One transaction, three tables
Every analyst action writes the review row, the session event and the audit row together or not at all. That is what makes the trail trustworthy enough to put a name next to a decision about a person.
Decline — the one place the concept slows you down on purpose

D does not decline. It opens a reason picker, focused, keyboard-navigable, and the decline writes only once a reason is chosen. Approve is one key because approving a real customer who is standing at a counter is the common case; declining is a judgement about a person and it gets one deliberate extra step.

DOC_EXPIREDUNDER_AGEFACE_BLOCKLIST_HIT DOCUMENT_BLOCKLIST_HITUSER_BLOCKLIST_HITIP_TOR INJECTION_DETECTEDCHALLENGE_NONCE_MISMATCHLIVENESS_ATTEMPTS_EXHAUSTED_HARD Analyst judgement — write a reason
What the customer sees
"We could not verify your ID." No reason code, no score, no hint about which signal fired. Telling a fraudster which check caught them is how you train them past it. The reason code lives in the console, the export and the audit log.
Blocklisting is a separate act
Declining a session does not add anyone to a list. L is its own key with its own audit row, because "this document is not good enough today" and "this person is banned" are different sentences and the console should never turn one into the other by accident.
Tab 4 · secondary on purpose

The table is where you answer a question. The queue is where you do the work.

Same columns Didit's verifications list has, plus the two it does not: the reason codes that put a session in review, and the channel it came through. Four filters, all multi-select, all reflected in the URL so a filtered view is a link you can paste to another analyst. Clicking a row opens the inspector — there is one session surface in this concept, not two.

The four filters, and why these four
StatusAll ten literals, multi-select. "Everything not finished" is three chips, not a saved view
WorkflowFour today. A version selector appears once a workflow has more than one
Reason codeThe filter Didit does not have. "Every barcode mismatch this month" is one chip
Channelhosted · embedded · pos (with store) · import. Where a session came from changes how you read it
Filters compose with AND across kinds and OR within a kind, which is the only combination anyone actually means. The state is in the URL.
Columns kept from Didit, and the two added

Kept, and spelled identically: session number, user, status, workflow, channel, vendor data, created. Dropped: the phone column, which is empty on every row in the live console. Added: reason codes and scores, both of which exist only because we now own the engine that produces them — Didit's table cannot show you why something is in review without opening it.

Export
CSV of exactly what is on screen, filters applied, plus the decision JSON as one column. The same rows are available on GET /v3/sessions/ with the same filter names, so a script and the screen never disagree.
